# NF08: нагрузочная проверка и финальная приёмка

Исторические результаты предыдущих прогонов от 11 ноября 2026 г. сохранены ниже без изменения их исходных JSON. Для TASK-007 отдельно выполняется сравнение штатной доставки до/после с тем же профилем NF08. Источник требований: `docs/specs/04-system-integration.md`, NF08, разделы 7 и 10. Каждый прогон создаёт временный Compose project и чистый PostgreSQL volume; после успешного отчёта удаляется только этот project и том. Актуальная повторная сверка требований ведётся в [матрице приёмки](acceptance.md).

## Воспроизведение

Из корня репозитория в PowerShell с Java 21, Node.js и Docker Compose:

```powershell
$env:JAVA_HOME = '<путь-к-Java-21>'
& .\scripts\run-nf08.ps1 -DrainSeconds 120
```

Linux Bash использует `bash scripts/run-nf08.sh`; Windows запускает `& .\scripts\run-nf08.ps1 -DrainSeconds 120`. Оба штатных запуска используют fixed delay 1000 мс и максимум 16 последовательных доставок за тик, как приложение. Для точного воспроизведения прежнего однозаписного worker можно передать `-WorkerMaxItemsPerTick 1` в PowerShell или `NF08_WORKER_MAX_ITEMS_PER_TICK=1` в Bash. Отдельный исторический профиль с 50 мс запускается только при явном `-WorkerPollIntervalMs 50` или `NF08_WORKER_POLL_MS=50`; он не подтверждает штатную конфигурацию. Скрипты сохраняют машинные отчёты, а текстовый отчёт обновляется вручную после проверки измерений.

Раннер собирает backend и runtime-зависимости Maven Wrapper, поднимает PostgreSQL, API и эмулятор, ждёт их готовности, сбрасывает и проверяет режимы сбоев, проверяет фактические квоты, вызывает `scripts/prepare-nf08.ps1`, затем запускает внешний Node.js генератор. Выбираются свободные loopback-порты и уникальное имя Compose project. Отчёт команды и исходный JSON сохраняются в игнорируемом `backend/target/performance/`.

Подготовку можно вызвать отдельно в уже запущенном проекте `compose.performance.yaml`:

```powershell
& .\scripts\prepare-nf08.ps1 -ProjectName <имя-nf08-проекта>
```

Она пересоздаёт только задания с `request_key` `nf08-fixture-*`, проверяет связанные строки и выгружает список фикстур. Создаётся 5000 записей: 2500 владельца Alice и 2500 Bob; у каждого владельца по 1250 статусов SUCCEEDED и FAILED. Все 5000 имеют состояние outbox DONE, три события истории, согласованную запись внешнего ledger с `executions=1`; `operator_scope` даёт оператору 2500 строк Alice и 0 строк Bob. Повторная подготовка очищает этот собственный префикс и создаёт полный набор заново. Демо-набор раздела 7 остаётся отдельным и содержит семь заданий.

## Результат

P95 рассчитан по времени round-trip от начала HTTP-запроса до получения его тела. Все завершённые запросы включены в p95; ошибок и таймаутов не было.

| Операция | Всего | Успешно | Ошибки | Таймауты | p95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| GET список | 812 | 812 (200) | 0 | 0 | 1182.9 ms |
| GET карточка | 814 | 814 (200) | 0 | 0 | 1108.3 ms |
| **Чтения вместе** | **1626** | **1626** | **0** | **0** | **1110.8 ms / лимит 2000 ms** |
| POST создание | 811 | 811 (200) | 0 | 0 | 1201.0 ms |
| PATCH ответственного | 810 | 810 (200) | 0 | 0 | 1193.3 ms |
| **Изменения вместе** | **1621** | **1621** | **0** | **0** | **1197.4 ms / лимит 3000 ms** |
| **Всего в измерении** | **3247** | **3247** | **0** | **0** | — |

В каждом клиентском цикле порядок запросов продолжался после завершения предыдущего; фактические количества операций отличаются максимум на четыре запроса (814 и 810). Причины ошибок и HTTP-коды записываются отдельно; в итоговом прогоне все ответы были 200. P95 вычислен методом ближайшего ранга: отсортированная выборка всех попыток, индекс `ceil(0.95 * N) - 1`; таймауты и ошибки также попадают в выборку.

### Время до внешнего исполнения

Внешняя таблица `executor.executions` хранит `executed_at`, выставляемое PostgreSQL при первой фиксации операции. Измерение вычитает `tasks.created_at` из этой отметки в той же БД.

| Снимок | Принято через POST | Внешне исполнено | Не завершено локально |
| --- | ---: | ---: | ---: |
| На границе 120-секундного измерения | 811 | 372 | 440 |
| После дополнительного окна до 120 секунд | 811 | 811 | 0 |

Столбцы пересекаются: SQL считал `unfinished`, если outbox ещё не DONE, локальный результат PENDING или внешняя запись отсутствует. Поэтому одно из 372 внешне исполненных заданий одновременно входит в 440 локально незавершённых; внешняя запись отсутствовала для 811 − 372 = 439 заданий. Оба счётчика относятся к одним `measurement`-ключам, без прогрева. Снимок сделан после завершения запросов, начатых до конца окна, а не точно в 120.000 секунды.

Для новых прогонов генератор дополнительно выдаёт `externallyNotExecuted` и `executedButLocallyUnfinished`; проверка расчёта на сохранённых числах и невозможных наборах выполняется командой `node --test scripts/performance/nf08-counts.test.mjs`. Сохранённые исходные JSON предыдущих прогонов оставлены без изменений и могут не содержать этих полей.

При Windows-регрессии с `DrainSeconds=0` обнаружено ещё одно расхождение: первый SQL-запрос насчитал 395 внешних исполнений, второй уже получил 397 измерений времени. Два исполнения произошли между запросами; [исходный JSON регрессии](nf08-windows-regression-2026-11-11.json) сохранён, а его выборка времени не относится к тому же снимку, что счётчики. Теперь все счётчики и времена выбираются одним SQL-оператором, а генератор проверяет равенство числа времён и внешних исполнений. Итоги старых прогонов выше сохранены с указанием их происхождения.

Повторная Windows-регрессия после исправления выполнила 3294 запроса без ошибок и таймаутов: 824 списка, 824 карточки, 823 создания и 823 изменения. P95 чтений — 1100.9 мс, изменений — 1110.7 мс; фактические лимиты — 2 CPU/4 GiB, polling — 50 мс. В едином снимке из 823 созданий 388 исполнены внешне и имеется ровно 388 временных измерений; 436 не завершены локально, из них 435 ещё не исполнены внешне и одно уже исполнено. Дополнительное ожидание было отключено (`DrainSeconds=0`), поэтому завершение оставшейся очереди в этом прогоне не наблюдалось. [Исходный JSON атомарного снимка](nf08-windows-atomic-2026-11-11.json) сохранён отдельно.

Для всех 811 измерительных POST после дренирования: медиана от создания записи до внешней фиксации — 48.38 s, p95 — 63.30 s, среднее — 47.64 s. Время внешней доставки приводится отдельно и не включается в p95 локального HTTP API.

## Отдельный прогон со стандартным polling 1000 мс

11 ноября 2026 г. выполнен отдельный Linux-прогон `NF08_WORKER_POLL_MS=1000 bash scripts/run-nf08.sh`. Генератор и раннер работали в отдельном Linux-контейнере с сетью host вне квот трёх измеряемых сервисов Docker Desktop; PostgreSQL, API и эмулятор использовали те же суммарные 2 CPU/4 GiB, подтверждённые HostConfig и cgroup. Исходный машинный результат сохранён в [nf08-linux-standard-2026-11-11.json](nf08-linux-standard-2026-11-11.json).

Среда: Docker Engine 29.2.1, Compose CLI 5.7.0, Linux kernel `6.6.87.2-microsoft-standard-WSL2`, Node 24.22.1, npm 11.12.1, Maven 3.10.0, Spring Boot 4.1.2 и PostgreSQL 17.11. В JSON поле `java` сохранило первую строку `JAVA_TOOL_OPTIONS`, а не номер Java. После прогона отдельно проверен `eclipse-temurin:21-jre` с digest `sha256:0b99b3376fbb50dbf9c0af8535fdd5b8eb0d3fdfc8b1e4967f383b6919f6901a`, использованный при сборке: Temurin 21.0.13. Следующий запуск записывает полный вывод `java -version`.

Прогрев длился 30 секунд и завершил 801 запрос; измерение длилось 120 секунд и завершило 3415 запросов. Результаты прогрева не входят в API p95, но созданные при нём задания остаются в очереди доставки.

| Операция | Всего и успешно | Ошибки / таймауты | p95 всех попыток |
| --- | ---: | ---: | ---: |
| GET список | 855 | 0 / 0 | 1097.6 мс |
| GET карточка | 852 | 0 / 0 | 1086.4 мс |
| **Чтения вместе** | **1707** | **0 / 0** | **1093.3 мс / лимит 2000 мс** |
| POST создание | 853 | 0 / 0 | 1107.0 мс |
| PATCH назначения | 855 | 0 / 0 | 1099.8 мс |
| **Изменения вместе** | **1708** | **0 / 0** | **1101.4 мс / лимит 3000 мс** |

На снимке после окна измерения все 853 созданных в измерительной фазе задания оставались незавершёнными локально, внешний ledger не содержал ни одного из них. После дополнительного ожидания 120 секунд внешне исполнены 40 и локально не завершены 813. Для этих **40**, а не для всех 853 заданий: p50 от локального создания до внешней фиксации — 218.27 с, p95 — 233.79 с, среднее — 218.66 с. Временный том затем удалён; завершение оставшихся 813 в этом прогоне не наблюдалось. Вероятная причина очереди — последовательная обработка с паузой 1000 мс и задания, накопленные при прогреве; точное распределение запросов прогрева исходный JSON не сохраняет. NF08 не задаёт порог времени внешнего исполнения, однако эта очередь существенно ограничивает пропускную способность штатной конфигурации.

Таким образом, оба проверенных распределения ресурсов проходят API-пороги в соответствующих условиях; 50 мс — специальная настройка performance Compose, 1000 мс соответствует обычному приложению. Данные отдельных прогонов нельзя считать прогнозом производственной ёмкости.

Повтор Linux-профиля после изменения учёта и обработки сигналов сохранён в [nf08-linux-atomic-regression-2026-11-11.json](nf08-linux-atomic-regression-2026-11-11.json). При 1000 мс, 30 с прогрева и 120 с измерения он выполнил 3059 запросов без ошибок и таймаутов; p95 чтений — 1191.3 мс, изменений — 1212.2 мс. На границе измерения все 766 созданных в измерительной фазе заданий оставались незавершёнными и не имели внешней записи. Дополнительное ожидание в этом повторе отключено (`NF08_DRAIN_SECONDS=0`), поэтому время внешнего исполнения не наблюдалось; оценка очереди после 120 с ожидания приведена в предыдущем абзаце.

## Исправление превышения при первом прогоне

Первая попытка имела распределение CPU backend/PostgreSQL/эмулятор `0.75/1.0/0.25`. Чтения показали p95 2201 ms и превысили NF08; изменения — 2400 ms. `cpu.stat` backend после прогона показал throttling в 1624 из 2385 периодов. Postgres и эмулятор при этом оставались почти незагружены. CPU и память перераспределены в пользу backend при неизменной общей квоте 2 CPU/4 GiB; итоговый профиль выше прошёл пороги.

Во втором проходе API-пороги уже выполнялись, но фоновой обработчик с обычным односекундным polling не успевал за потоком создания и оставлял очередь. Для производительного Compose-профиля интервал polling стал настраиваемым и задан 50 ms; дедлайны `next_attempt` и ограниченный backoff неизменны. Итоговый прогон выполнил все 811 операций до конца дополнительного 120-секундного окна. Значения внешнего p95 здесь являются наблюдением профиля и отдельный нормативный порог для них в NF08 не задан.

## Известные ограничения

- Статический пользовательский каталог и локальные demo-пароли подходят только для демонстрации; области оператора отдельно не администрируются.
- В NF08 backend-профиль принудительно выставляет polling 50 ms; стандартный профиль приложения оставляет default 1000 ms. Внешнее время, полученное в этом отчёте, относится к указанной настройке и нагрузке, а не к production SLA.
- Даже с polling 50 ms 440 операций оставались незавершёнными локально при снимке после измерения; из них 439 ещё не имели внешней записи. Все завершились в дополнительном окне 120 секунд. NF08 задаёт пороги только для локального API и не задаёт отдельный порог внешней доставки.
- Профиль выполняется на локальном Docker Desktop и не прогнозирует производственную ёмкость.

## TASK-007: штатная доставка до и после ограниченной пачки

Инженерная цель этого изменения — обработать все принятые измерительные задания в прежнем дополнительном окне до 120 секунд при сохранении API p95. Это цель улучшения, а не самостоятельный порог спецификации: NF08 задаёт API p95 и требует измерять время до внешнего исполнения, но не задаёт отдельного предела внешней задержки.

Оба запуска выполнялись в отдельных чистых Compose project на той же Docker Desktop/WSL2 среде, при лимитах 2 CPU / 4 GiB, 5000 фикстурах, 20 последовательных клиентах, прогреве 30 секунд, измерении 120 секунд, обычных режимах эмулятора и drain до 120 секунд. Использованы один и тот же код API и ресурсы; до — эквивалент прежнего `deliverOne()` раз за тик (batch=1), после — штатный предел 16 записей за тик. В обоих случаях fixed delay равен 1000 мс. Исходные машинные отчёты сохранены без изменений: [до](nf08-task007-before-batch-2026-11-11.json), [после](nf08-task007-after-batch-2026-11-11.json).

До batch change измерительные задания не начали доставляться до исчерпания прогревной очереди; после полного номинального drain осталось 735 заданий. Эта очередь объясняется прежним циклом «одна синхронная доставка, затем fixed delay 1000 мс». После изменения на границе измерения ещё было 409 задач, но worker обработал их в drain за 57 секунд; итоговая очередь равна нулю, внешне исполнены все 783 измерительных задания, локально незавершённых нет. Таким образом, цель полного drain в пределах 120 секунд выполнена; API p95 остался ниже формальных 2/3 секунд.

Операционный p95 вычислен методом ближайшего ранга по всем измерительным запросам, включая ошибки и таймауты. В каждом запуске измерено около 780 каждой из четырёх операций; ошибки, таймауты и бизнес-отказы равны нулю. Отчёт раннера дополнительно проверил ненулевые выборки API, внешней задержки и фазовых времён, а JSON сохраняется до выставления ошибки профиля. Внешняя задержка измеряется от `tasks.created_at` до `executor.executed_at` в одной БД; выборка включает только задания, у которых есть внешняя запись на момент после drain.

### Времена внутренних фаз

Значения ниже — p95 длительностей в миллисекундах. `claim` включает локальный запрос/захват outbox, `HTTP` — полный синхронный вызов эмулятора, `apply` — локальная проверка lease/версии и применение. Эмулятор отдельно измеряет получение JDBC-соединения, чтение заблокированной строки `fault_modes` и внешнюю транзакцию.

| Фаза | До: выборка / p95 | После: выборка / p95 |
| --- | ---: | ---: |
| Worker claim | 249 / 107.624 ms | 988 / 100.906 ms |
| HTTP эмулятора | 249 / 202.234 ms | 988 / 193.001 ms |
| Локальное применение | 249 / 100.776 ms | 988 / 100.065 ms |
| JDBC connection эмулятора | 240 / 22.699 ms | 972 / 50.855 ms |
| `fault_modes FOR UPDATE` | 240 / 2.268 ms | 972 / 2.700 ms |
| Транзакция executor | 240 / 86.758 ms | 972 / 12.050 ms |

Замер не подтвердил, что блокировка `fault_modes` является ограничителем: её p95 около 2.3–2.7 ms, существенно ниже p95 HTTP и claim. Поэтому блокировка и атомарное потребление одноразовых режимов не менялись; стабильный `operationId`, уникальный внешний ledger и `executions=1` остаются прежними. Исправлена подтверждённая причина пропускной способности — один запуск `deliverOne()` перед каждой секундной задержкой — ограниченным последовательным циклом до 16 задач. Параллельные доставки не понадобились.

### Конфигурация и область результата

Обычная конфигурация приложения и оба новых запуска используют `EXCHANGE_WORKER_FIXED_DELAY_MS=1000`; штатный предел `EXCHANGE_WORKER_MAX_ITEMS_PER_TICK=16`. Исторические профили с 50 ms, приведённые выше, относятся к отдельной экспериментальной конфигурации и не подменяют эти результаты. Все три сервиса получили в HostConfig и cgroup ровно 2.0 CPU и 4096 MiB; тестовый генератор работал в отдельном ненормированном Linux-контейнере, не входящем в Compose resource totals. Docker Engine был Docker Desktop на Windows 11 с Linux/WSL2 ядром 6.6.87.2; Docker/Compose 29.2.1/5.7.0, Temurin 21.0.13, Maven Wrapper 3.10.0, PostgreSQL 17.11, Node 24.22.1.

Для повтора на Linux-хосте: `bash scripts/run-nf08.sh`. Для Docker Desktop, где раннер должен быть подключён к внутренней сети Compose, соберите `docker build -t secreate-nf08-runner -f scripts/Dockerfile.nf08-runner .` и запустите его с Docker socket и монтированием репозитория: `docker run --rm -v /var/run/docker.sock:/var/run/docker.sock -v "$PWD:/workspace" -w /workspace -e NF08_RUNNER_IN_COMPOSE_NETWORK=1 -e NF08_WORKER_POLL_MS=1000 -e NF08_WORKER_MAX_ITEMS_PER_TICK=16 -e NF08_DRAIN_SECONDS=120 secreate-nf08-runner bash scripts/run-nf08.sh`. В PowerShell используйте `& .\scripts\run-nf08.ps1 -DrainSeconds 120`; профиль также можно параметризовать для batch=1 через `-WorkerMaxItemsPerTick 1`.
