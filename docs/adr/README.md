## Когда нужен ADR

ADR нужен, если решение дорого отменить, оно меняет важную архитектурную границу или достаточно неочевидно, чтобы будущий сопровождающий спросил «почему так». Типичные случаи:

- замена или сознательный отказ от ключевой библиотеки;
- изменение стратегии аутентификации, прав доступа, генерации контракта API или транспорта;
- изменение моделей данных, требующее миграции существующих данных;
- изменение формата ключей хранилища и других внешне наблюдаемых форматов;
- изменение стратегии тестирования;
- существенное ограничение безопасности или приватности;
- неочевидный компромисс, обоснование которого должно пережить задачу.

ADR не нужен для имён, форматирования, рутинного рефакторинга, обычных исправлений и реализации решения, уже описанного в существующем ADR.

## Жизненный цикл

- ADR фиксирует **принятое** решение. Идеи и предложения живут в задачах, пока не приняты.
- Путь: `docs/adr/NNNN-short-slug.md`; номера стабильны и не переиспользуются.
- Исторические ADR не удаляются, не перенумеровываются и не переписываются молча. Если решение заменяется, создайте новый ADR и пометьте старый `Заменено ADR NNNN` (или `Частично заменено`) с датой; новый ADR указывает, что он заменяет. Уточнения без смены решения записываются в раздел «Дополнения».
- Каждый новый ADR добавляется в таблицу выше и в боковое меню `docs/.vitepress/config.ts`.
- Последствия включают негативные стороны и компромиссы. Другие документы ссылаются на обоснование, а не копируют его.
