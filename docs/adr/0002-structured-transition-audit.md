# ADR 0002. Структурированное содержание событий аудита

## Статус

Принято

Дата: 2026-11-11

## Контекст

`exchange_events` сохранял объект, тип события, actor и время, но автоматический переход бизнес-состояния записывал только `RESULT_APPLY`. После следующего изменения невозможно определить из истории старый и новый статус или версию. Виды событий различаются: применение результата, доставка, попытка, сверка и ручное восстановление несут разные детали.

## Решение

Добавить в `exchange_events` поле `details jsonb not null default '{}'` с проверкой, что корень JSON — объект. Записывать детали вместе с событием в той же транзакции, что и соответствующее изменение состояния. События перехода результата содержат прежний и новый бизнес-статус и версии, входящий результат, решение и старое/новое состояние доставки. Операторские сверки и восстановления указывают идентификатор снимка/команды и фактический переход.

Операторский API возвращает `task_id` и объект `details` только внутри существующей проверки OPERATOR и `operator_scope`. Карточка показывает старое и новое значение. Ключи идемпотентности и сырые внешние тела не копируются в общий журнал: snapshots сверки остаются в `reconciliations`, данные назначений — в `assignment_audit`.

Существующие строки мигрируют с `{}` и сохраняют текущие event/actor/time. Восстановить исторические старые значения статусов, которые не сохранялись прежней схемой, невозможно; миграция их не выдумывает.

## Рассмотренные альтернативы

- Добавить отдельные nullable old/new колонки для каждого типа состояния. Отклонено: все типы событий получили бы набор неиспользуемых полей, а модель не покрыла бы детали попытки и сверки.
- Создать отдельную таблицу для каждой категории событий. Отклонено: UI и API получили бы несколько источников истории, хотя порядок и авторство общие.
- Хранить только текстовое описание. Отклонено: оно неудобно валидировать, читать на UI и использовать для последующих интеграций.

## Последствия

### Положительные

- История фиксирует проверяемые прежние и новые значения в той же транзакции.
- Один API-список показывает последовательность переходов разных видов, сохраняя нормализованные аудит-таблицы для назначения и сверки.
- Ограничение объектной формы и PostgreSQL-тесты защищают контракт от пустых или непрозрачных событий.

### Негативные / компромиссы

- `jsonb` гибок, поэтому ключи события проверяются интеграционными тестами, а не схемой для каждой версии.
- Старые события остаются с пустыми `details`; отсутствующие исторические значения нельзя восстановить задним числом.
- Для отображения UI должен интерпретировать поля по типу события; неизвестные поля остаются доступны в JSON API.
