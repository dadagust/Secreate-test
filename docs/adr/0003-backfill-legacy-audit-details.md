# ADR 0003. Восстановление доступных деталей исторического аудита

## Статус

Принято

Дата: 2026-11-12

Частично уточняет решение о миграции исторических событий из ADR 0002.

## Контекст

Миграция V8 добавила `exchange_events.details`, но заполняла старые строки пустым JSON-объектом. У части событий до V8 рядом с журналом уже хранились авторитетные исходные данные: внешний ledger эмулятора, снимки сверки, конфликт и команда восстановления. Оставлять такие события пустыми означает терять детали, которые можно восстановить без догадок. Одновременно текущую строку `tasks` нельзя безусловно использовать как исторический снимок: её состояние могло измениться после события.

## Решение

Миграция V9 обрабатывает события задания в порядке их неизменяемого identity `exchange_events.id` и восстанавливает только проверяемые поля:

- `CREATED` — неизменяемые владелец и заголовок из `tasks` плюс начальные значения, заданные контрактом;
- `ATTEMPT_n` и `AMBIGUOUS_RETRY` — номер попытки из имени события и последовательное состояние доставки;
- применение результата — внешний результат из `executor.executions` или сохранённого снимка со `FOUND`;
- конфликт — значения из `result_conflicts` для того же задания, номера попытки и времени события;
- сверка и решение — соответствующий снимок `reconciliations` по автору и времени;
- ручное восстановление — запись `recovery_commands` и состояние, восстановленное по событиям до команды.

Если надёжный источник отсутствует, миграция записывает `legacyPayloadAvailable: false`, причину и `null` для неизвестных значений. Она не выводит старое/новое значение из текущей строки задания. После backfill миграция снимает default `{}` и добавляет ограничение, запрещающее пустые `details` для новых событий.

NF08 SQL seed также создаёт полные события `CREATED`, `ATTEMPT_1` и `RESULT_APPLY`, а проверка отвергает пустые audit details.

## Рассмотренные альтернативы

- Заполнять результат текущими полями `tasks`: отклонено, потому что это может выдать современное значение за историческое.
- Оставить все старые детали пустыми: отклонено для событий, у которых есть проверяемая нормализованная запись или внешний ledger.
- Удалить старые события: отклонено, поскольку журнал нужен для аудита и восстановления.

## Последствия

### Положительные

- История получает доказуемые старые/новые значения там, где источник сохранился.
- Неизвестные исторические значения видны как пробел данных с причиной, а не как выдуманное состояние.
- Новые application и NF08 seed-события не могут записываться с пустыми деталями.

### Негативные / компромиссы

- Для некоторых старых результатов без ledger и снимка сверки исходный payload навсегда утрачен; V9 помечает эти поля недоступными.
- V9 требует сначала запустить эмулятор при compose-старте, чтобы внешний ledger был доступен до Flyway-миграции backend; при отсутствии ledger миграция использует сохранённые снимки, иначе явно помечает payload недоступным.
