# Подготовка плана реализации

Подготовь **implementation-ready план текущей задачи без внесения изменений в проект**.

Главная цель:

> Сначала понять фактическое состояние репозитория, ограничения и затрагиваемые границы, затем составить конкретный и проверяемый план реализации, по которому другой coding-agent сможет начать работу без повторного исследования задачи.

Этот промпт предназначен только для **planning**. **Не реализуй план.**

Постоянный план STANDARD/LONG задачи живёт в задаче Backlog.md (`AGENTS.md`). Результат этого промпта — план для согласования и последующего переноса в Backlog.md, а не новый source of truth.

---

## 1. Режим работы

Работай в режиме **только на чтение**.

**Не изменяй**: код, тесты, конфигурацию, зависимости и lock-файл, generated-файлы, документацию и ADR, `PROGRESS.md`, `WORKLOG.md`, задачу Backlog.md, Git index, ветки и историю Git. Не создавай отдельные файлы планов (`PLAN.md`, `TASK_PLAN.md`, `IMPLEMENTATION_PLAN.md`, `docs/plans/*` и т. п.). Не запускай autofix, генерацию и команды, которые изменяют tracked-файлы; не устанавливай зависимости и инструменты.

### Проверки во время planning

Выполняй только те проверки, которые нужны, чтобы установить фактическое текущее состояние, подтвердить существенное предположение или разрешить неопределённость, влияющую на план: чтение файлов, поиск по коду, Git inspection, просмотр generated output, точечные проверки без изменений, запуск существующего теста, если его результат действительно нужен для понимания текущего поведения.

Какие скрипты безопасны и что учесть — в разделе «Команды для проверок только на чтение» [`prompts/README.md`](README.md). Не запускай полный verification workflow, dev-серверы, watch-режимы, долгоживущие и интерактивные процессы без реальной необходимости исследования. Если пришлось запустить процесс (например, dev-сервер backend или frontend), проверь, что порт свободен, и назови запущенные и остановленные процессы в ответе.

**Verification plan** ниже предназначен для будущего исполнителя: наличие команды в нём не означает, что её нужно запускать сейчас.

### Секреты

План может цитировать конфигурацию, env и фрагменты кода. Не включай значения токенов, паролей, ключей API, cookie, заголовков авторизации, содержимого `.env*` и персональные данные: замени на `<скрыто>` и укажи, где находится значение.

## 2. Сначала восстанови актуальный контекст

Если доступны инструменты репозитория:

1. прочитай корневой `AGENTS.md` и релевантные вложенные `AGENTS.md`;
2. прочитай `PROJECT_OVERVIEW.md` и релевантную часть `PROGRESS.md`;
3. прочитай относящуюся к задаче задачу Backlog.md и `WORKLOG.md`, если он относится к ней;
4. выполни `git status --short`, определи ветку и HEAD, просмотри релевантный `git diff` и `git diff --cached`;
5. Изучи относящиеся к задаче код, тесты, конфигурацию, документацию и существующие манифесты: корневой package.json, а после их появления — pom.xml и frontend/package.json.

Не проводи полный аудит проекта — исследуй только то, что нужно для правильного плана. Если источник недоступен, не придумывай его состояние: отметь как непроверенное.

### Если worktree не чистый

Ничего не `reset`, `restore`, `checkout` или `stash`. Определи, какие изменения относятся к текущей задаче; отличай committed baseline от текущего working tree; учитывай уже выполненную работу и не планируй её повторно. Не считай незавершённый diff проверенным поведением и не принимай случайный незавершённый код за архитектурный precedent. Если происхождение критичного изменения установить нельзя, отметь это как uncertainty.

План строится относительно **фактического текущего worktree**, но отличает подтверждённую реализацию от незавершённых изменений.

---

## 3. Разделяй фактическое состояние и обязательные правила

У planning два разных вопроса, их не смешивай:

2. **Каким правилам должна соответствовать реализация?** Отвечай по `AGENTS.md` (включая «Архитектурные инварианты» и «Публичные контракты»), применимым `AGENTS.md` пакетов (`backend/AGENTS.md`, `frontend/AGENTS.md`), действующим ADR в `docs/adr/` и `docs/project/conventions.md`.

Существующий код не отменяет обязательное правило только потому, что нарушение уже есть в репозитории. Если реализация противоречит правилу: зафиксируй расхождение, определи, относится ли его устранение к текущему scope, не используй нарушающий код как precedent и не расширяй задачу исправлением несвязанного нарушения.

Все упоминаемые в плане файлы, symbols, scripts, маршруты, методы API, зависимости, переменные окружения и generated contracts должны быть подтверждены репозиторием либо явно отмечены как ещё не существующие и планируемые.

---

## 4. Зафиксируй задачу

До проектирования решения сформулируй:

```text
Goal:
...

Expected outcome:
...

Acceptance criteria:
- ...

In scope:
...

Out of scope:
...

Task level:
SMALL / STANDARD / LONG
```

Уровень задачи определяй по текущему `AGENTS.md`. Не повышай его только потому, что составляется подробный план. Не расширяй scope молча.

Если невозможно однозначно установить, **какую именно задачу нужно планировать**, не выбирай её сам по названию ветки или случайному diff: статус `BLOCKED`, укажи, какого контекста не хватает.

---

## 5. Факты, предположения и статус плана

Для существенных выводов различай **CONFIRMED** (подтверждено кодом, конфигурацией, тестом, runtime evidence или канонической документацией), **ASSUMPTION** (разумное, но не подтверждённое) и **UNKNOWN** (данных недостаточно). Не маскируй предположение под факт.


| Статус                     | Когда                                                                                                                                                                                                                      |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **READY**                  | существенных неизвестностей нет, предположений, влияющих на реализацию, нет                                                                                                                                                |
| **READY WITH ASSUMPTIONS** | остались только локальные обратимые предположения, не влияющие на архитектуру, контракты, безопасность и миграции; их безопасно подтвердить в ходе реализации                                                              |
| **BLOCKED**                | есть неизвестность, которую небезопасно разрешать во время реализации; до кода нужно решение, evidence или уточнение. Укажи причину и следующий шаг (например, для бага без подтверждённой причины — `investigate-bug.md`) |

---

## 6. Изучи существующую реализацию

До предложения изменений проследи фактический путь сценария через React-компоненты, API, Spring-контроллеры, сервисы и хранилище, а также тесты и документацию. Если реализация ещё не существует, отметь это и планируй её без выдуманных путей. Ссылайся на подтверждённые файлы и symbols.

Плохо:

```text
нужный компонент
соответствующий сервис
какой-то API hook
```

Если задача решает уже решённую в проекте проблему, опирайся на существующий аналог (соседний эндпоинт того же приложения, фичу с тем же устройством), когда он действительно релевантен, но не копируй его механически: эталонная реализация в документации проекта не названа, а существующий код может нарушать правила (раздел 3). Generated-файлы читай для понимания фактического интерфейса; целью ручного изменения они быть не могут.

### Порядок типовых задач и skills проекта

Собственных skills проекта для типовых задач (эндпоинт, страница, миграция) пока нет ([инструменты агентов](../docs/agents/tooling.md), «Состав»). Порядок шагов и известные ловушки записаны в `AGENTS.md` пакетов — строй план по ним, а не заново:

| Задача                            | Где порядок                                                                                                                                  |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| API | Контракт, проверка доступа, сервис и потребитель; конкретные файлы определяются существующим кодом. |
| Модель и миграция | Версионируемая миграция PostgreSQL, совместимость и тесты. |
| Страница или фича frontend | React-компоненты, состояния и доступность; команды по фактическому frontend/package.json. |

Общие skills (`writing-plans`, `test-driven-development`, `systematic-debugging`, `codebase-design`) подключай по их описанию. Сверяй правила с текущим кодом: если `AGENTS.md` или skill расходится с репозиторием, прав код, а расхождение отметь в плане как находку.

---

## 7. Проверь затрагиваемые границы

Исследуй только применимые категории и фактические архитектурные границы. Не планируй ручную правку сгенерированных файлов и публикацию секретов во frontend.

- **API и серверное состояние**: контроллеры Spring, валидация, сервисы, права, договорённые контракты и обработка ошибок. Генерируемые файлы меняй через их источник и существующую команду генерации.
- **UI**: компоненты React, состояние загрузки, пустого результата и ошибки, доступность, клавиатура и адаптивность.
- **Зависимости**: перед добавлением — проверка, что стек не решает задачу, актуальная документация и совместимость (`AGENTS.md`, «Зависимости»); причина добавления — в плане.
- **Безопасность и приватность**: недоверенный ввод, персональные данные, секреты в клиентском бандле, аутентификация, права доступа, хранение и логирование.

---

## 8. Если это bug fix

Если задача требует исправить баг, но root cause ещё не подтверждён, **не придумывай permanent fix и не составляй speculative implementation plan**: статус `BLOCKED`, причина «root cause не подтверждён», следующий шаг — `investigate-bug.md`.

Если root cause уже доказан — используй подтверждённую failure chain как основу плана и планируй исправление причины, а не маскировку симптома.

---

## 9. Выбери минимальный подход

Подход соответствует существующей архитектуре, использует подходящие существующие абстракции, меняет минимум владельцев и слоёв, не добавляет зависимостей и абстракций без необходимости, не включает несвязанный рефакторинг и сохраняет корректное поведение.

Не генерируй несколько вариантов ради полноты. Альтернативы описывай, только если есть реальный технический или архитектурный выбор:

```text
Chosen approach:
...

Why:
...

Rejected alternative:
...

Why rejected:
...
```

Если решение меняет архитектурный инвариант или дорого в отмене — отметь необходимость ADR и второго прохода ревью (`AGENTS.md`).

---

## 10. Построй исполнимый план

Разбей реализацию на минимальные логически завершённые шаги. Каждый шаг отвечает: **что** изменить, **где**, **почему именно здесь**, **как проверить** этот шаг. Используй реальные пути и symbols, если они известны.

Хорошо:

```text
Шаг: обновить потребитель API в подтверждённом файле компонента.
Проверка: существующие frontend-тесты и сценарий в браузере.
```

Плохо:

```text
Step 2 — обновить frontend.
```

**Порядок** следует реальным зависимостям: контракт и серверная логика перед потребителем; миграции, конфигурация и тесты — по фактическому устройству проекта.

**Размер шага**: реализуем без нового архитектурного исследования, его diff можно проверить, для него есть конкретная проверка, для LONG он может быть контрольной точкой. Не дроби до механических действий («открыть файл», «добавить import»): планируй результаты, а не нажатия клавиш.

### LONG: декомпозиция

`AGENTS.md` требует для LONG задачу с декомпозицией и контрольными точками. Разбей план на подзадачи Backlog.md (родитель и подзадачи через `-p <id>`), для каждой укажи:

- результат и критерии приёмки;
- зависимости от других подзадач;
- что будет контрольной точкой в `WORKLOG.md` после её завершения;
- нужен ли второй проход ревью.

Порядок подзадач — по зависимостям; независимые можно отметить как параллельные.

---

## 11. Verification до coding

До реализации определи проверку каждого результата. Для агентского слоя используй `npm run check:agents`. Команды Maven Wrapper, frontend и Docker Compose выбирай после проверки существования wrapper, манифестов и соответствующих скриптов.

Для каждого теста назови поведение и ожидаемый результат, не придумывая существующие пути.

Каждый существенный критерий приёмки имеет автоматическую проверку, сценарий в браузере или рантайме, статическую проверку — либо объяснение, почему автоматическая проверка неприменима. Не оставляй важный критерий без способа доказательства.

**Финальные проверки** — `npm run check:agents` и применимые проверки приложения по фактическим манифестам; проверяй миграции, контракты и UI, когда они затронуты.

---

## 12. Migration, compatibility, документация


```text
Migration:
...

Backward compatibility:
...

Rollback:
...
```

**Документация**: меняй каноническую страницу, только если реализация меняет описанное поведение, API или workflow; не создавай новый документ, если у информации уже есть владелец. ADR — только для архитектурного решения по `AGENTS.md`, не для реализации уже принятой архитектуры. `PROJECT_OVERVIEW.md` — только по его критериям обновления.

---

## 13. Второй проход ревью

Если затрагивается область, для которой `AGENTS.md` требует второй проход ревью, включи его в план:

```text
implementation
→ relevant checks
→ final diff review
→ required second review pass (например, subagent reviewer)
→ исправление подтверждённых findings
→ final verification
```

Не называй ревью независимым, если оно выполняется в том же контексте.

---

## 14. Существующий план в Backlog.md

Если в задаче уже есть план, не начинай с нуля: сравни его с текущим состоянием репозитория, сохрани корректные части, исправь устаревшие и неподтверждённые, добавь недостающие шаги, убери фактически выполненные и подготовь **полную актуальную версию плана**. После неё кратко перечисли изменения относительно предыдущего плана и причины существенных. Не выдавай только delta, если без старого текста новый план нельзя выполнить самостоятельно.

Если старый план противоречит текущему коду или проверенному поведению, в вопросе текущего состояния прав репозиторий; обязательные правила `AGENTS.md` и ADR сохраняют силу.

Во время этого промпта задачу Backlog.md не изменяй. После согласования пользователь может попросить записать план туда — для этого в ответе есть раздел «Перенос в Backlog.md».

# Формат ответа

Шаблоны ниже — формат ответа, а не продолжение инструкций.

## Для STANDARD / LONG

```markdown
# Implementation plan

## 1. Цель

**Goal:** ...

**Expected outcome:** ...

**Acceptance criteria:**

- AC1 — ...
- AC2 — ...

**Task level:** STANDARD / LONG

**Plan status:** READY / READY WITH ASSUMPTIONS / BLOCKED (причина и следующий шаг)

## 2. Подтверждённое текущее состояние

Только факты, влияющие на решение:

- `path / symbol` → текущее поведение;
- `test / config / ADR` → evidence.

Незавершённые изменения worktree, относящиеся к задаче, отдели от committed baseline.

## 3. Scope

### In scope

- ...

### Out of scope

- ...

## 4. Ограничения и решения

- архитектурные границы и контракты;
- использованный skill проекта, если применимо;
- выбранный подход и существенные отвергнутые альтернативы, если они реально были.

## 5. План реализации

### Step 1 — <результат>

**Изменить:** `path / symbol`

**Что сделать:** ...

**Почему здесь:** ...

**Проверка:** ...

**Зависит от:** ничего / Step N

### Step 2 — ...

Для LONG — вместо шагов подзадачи: результат, критерии, зависимости, контрольная точка, второй проход ревью.

## 6. Verification plan

| Acceptance criterion | Что доказать | Проверка | Уровень                                        |
| -------------------- | ------------ | -------- | ---------------------------------------------- |

**Final project gates:** ...

## 7. Migration / compatibility

Только если применимо.

## 8. Документация / ADR

Только необходимые изменения.

## 9. Риски и неопределённости

Только непустые подразделы: Risks, Assumptions, Unknowns, Blocking questions (вопросы, без которых реализация небезопасна).

## 10. Изменения относительно существующего плана

Только если в задаче уже был план.

## 11. Готовность

- план основан на текущем репозитории: ДА / ЧАСТИЧНО / НЕТ
- релевантная реализация изучена: ДА / ЧАСТИЧНО / НЕТ
- dirty worktree учтён: ДА / НЕТ / НЕ ПРИМЕНИМО
- acceptance criteria и verification определены до coding: ДА / НЕТ
- migration/compatibility учтены: ДА / НЕТ / НЕ ПРИМЕНИМО
- ADR требуется: ДА / НЕТ
- второй проход ревью требуется: ДА / НЕТ
- blocking questions отсутствуют: ДА / НЕТ
- запущенные процессы: нет / перечень (все остановлены)
- можно начинать реализацию: ДА / НЕТ

## 12. Перенос в Backlog.md

Не выполняй — это готовые данные для записи после согласования (`docs/agents/task-workflow.md`). Каждое значение — одна строка без переносов: на Windows переносы внутри аргумента теряются.

- Описание (`-d`): Goal, Expected outcome, затронутые контракты из раздела 4 (или «контракты не меняются») и Out of scope из раздела 3 одной строкой.
- Критерии приёмки: по одному `--ac "..."` на критерий, в тексте — его проверка из Verification plan: `--ac "<критерий> — проверка: <команда, тест или сценарий>"`.
- План — через `task edit <id>`: первый шаг — `--plan "..."`, каждый следующий — отдельный `--append-plan "..."`. `task create` принимает `--plan` только для задачи, сразу создаваемой в активном статусе.
- Rollback из раздела 7 — отдельным `--append-plan "..."`, только если меняются зависимости, хранилище или контракты.
- Для LONG: подзадачи — `task create "..." -p <id родителя>` с их `--ac` и зависимостями `--dep`.
- Assumptions и Unknowns — `--append-notes "..."`.
```

## Для SMALL

SMALL-задаче задача Backlog.md не нужна (`AGENTS.md`), поэтому раздел переноса не нужен. Не раздувай ответ:

```markdown
# Implementation plan

**Goal:** ...

**Current state:** ...

**Acceptance criteria:**

- ...
```

# Инварианты

1. **Сначала исследование, потом план; во время planning не реализуй задачу.**
2. **Фактическое состояние определяет репозиторий, обязательные правила — `AGENTS.md` и ADR; существующее нарушение не становится precedent.**
3. **Постоянный план STANDARD/LONG живёт в задаче Backlog.md; второй source of truth не создавай.**
4. **Все ссылки на файлы, symbols, скрипты и контракты подтверждены или помечены как планируемые.**
5. **Типовые задачи планируй по `AGENTS.md` пакетов и skills проекта.**
6. **Каждый шаг имеет цель, область и проверку; verification определяется до coding и связана с критериями приёмки.**
7. **Generated code меняется через источник; владельцы состояния и границы не меняются молча; scope не расширяется.**
8. **Нет permanent fix бага без подтверждённого root cause.**
9. **Если критичное решение нельзя принять на основании evidence — `BLOCKED` лучше выдуманного плана.**
10. **План подробен настолько, насколько нужно для реализации, но не превращается в построчное описание будущего кода.**
