# Промпты

Промпты — шаблоны, которые пользователь сам вставляет в чат с агентом. Это не правила проекта.

- Промпт не переопределяет архитектуру, порядок работы, проверки качества и источники истины из `AGENTS.md` (корневого и пакетов). Он ссылается на каноническую документацию, а не копирует её.
- При конфликте промпта с `AGENTS.md` действуют текущая явная инструкция пользователя и правила приоритета из `AGENTS.md` (раздел «Источники истины»).
- Результат промпта, который уходит в другой чат или другую LLM, не содержит секретов: токены, пароли, cookie, коды OTP, содержимое `.env*` и персональные данные маскируются.
- Ни один промпт не коммитит и не делает push. Коммит — только по отдельной просьбе пользователя в текущей сессии (`AGENTS.md`, раздел «Git»).

«Меняет проект: нет» означает режим только на чтение: промпт запрещает менять код, конфигурацию, задачи Backlog.md, `WORKLOG.md` и `PROGRESS.md` и разрешает только штатные проверки из таблицы [команд](#команды-для-проверок-только-на-чтение).

`collect-docs.md` создан `docs-prompt-generator.md` со снимком проекта на commit из его Части B (TASK-002); при существенных изменениях проекта пересоберите его тем же генератором.

## Как вызвать промпт

1. Откройте агента в корне репозитория, чтобы у него были файлы, shell и Git. Без инструментов осмысленно работают только handoff-промпты (по истории чата, со сведениями о репозитории, помеченными как непроверенные) и `deep-research.md` для вопросов, не связанных с проектом.
2. Вставьте текст промпта целиком. В клиентах, которые подставляют содержимое файла по ссылке (например, `@prompts/implementation-plan.md` в Claude Code), можно сослаться на файл.
3. Допишите после промпта одну-три строки с данными: какую задачу, что проверить, какой вопрос. Что нужно каждому промпту — в разделе «Руководство по промптам».
4. Промпты с режимом только на чтение по возможности запускайте в новой сессии: ревью и проверка в том же контексте, где шла реализация, не являются независимыми (`AGENTS.md`, раздел «Второй проход ревью»).

Отдельного промпта для реализации нет: реализацию запрашивают обычным сообщением («Реализуй TASK-15 по плану в задаче»), агент работает по `AGENTS.md`, `AGENTS.md` пакетов и skills проекта. Если реализация продолжается в новой сессии — `continue-task.md`.

## Руководство по промптам

### `handoff-full.md` — полный перенос сессии

- **Когда:** сессия длинная, в ней много решений, поправок пользователя, отвергнутых вариантов и исследований, которые нужно перенести в новый чат, в том числе в LLM без доступа к репозиторию.
- **Когда не использовать:** нужна передача только текущей задачи — `handoff-compact.md`. Пауза или передача в том же worktree, где разговор переносить не нужно, — достаточно контрольной точки (в Claude Code её делает `/handoff`, skill `handoff`); новая сессия восстанавливается через `continue-task.md` без handoff.
- **Как вызвать:** вставить промпт в конец текущей сессии и при необходимости указать следующий шаг.
- **Результат:** один блок Markdown для копирования, до ~5000 слов. В репозитории меняются только `WORKLOG.md` и заметки активной задачи; если активной задачи нет, handoff это отмечает.
- **Дальше:** в новой сессии вставить `continue-task.md`, а после него — полученный блок. Разрешения на коммиты и push из старой сессии в новую не переходят.

### `handoff-compact.md` — перенос текущей задачи

- **Когда:** нужно передать одну незавершённую задачу новому чату или другому coding-агенту, а история разговора сама по себе не важна.
- **Когда не использовать:** важны хронология, поправки и контекст за пределами задачи — `handoff-full.md`. Задача SMALL и уже завершена — handoff не нужен, достаточно отчёта.
- **Как вызвать:** вставить промпт в текущей сессии. Если активных задач несколько, дописать: «Задача TASK-12». Можно указать получателя: «Передаю агенту Codex».
- **Результат:** блок на 800–2000 слов: цель, статус Git, проверки, решения, точка продолжения из 1–3 действий. Меняются только `WORKLOG.md` и заметки задачи.
- **Дальше:** как у `handoff-full.md` — новая сессия с `continue-task.md` и вставленным блоком.

### `continue-task.md` — продолжение незавершённой задачи

- **Когда:** новая сессия после сжатия контекста, перерыва или передачи; агент должен сам восстановить состояние по протоколу «Восстановление контекста» `AGENTS.md` и продолжить с первого незавершённого шага.
- **Когда не использовать:** задачи ещё нет или у неё нет плана — сначала `implementation-plan.md`. Нужно только оценить результат, не продолжая работу — `review-implementation.md` или `audit-after-changes.md`. Причина бага не подтверждена — `investigate-bug.md`.
- **Как вызвать:** вставить промпт. Если в `In Progress` несколько задач, дописать: «Задача TASK-12» — иначе агент спросит и остановится. Если есть handoff, вставить его после промпта. Новые решения писать явно: «Решение: отказались от X, делаем Y» — агент запишет их в заметки задачи как решение пользователя. Разрешение на коммиты, если оно нужно, дать в этой же сессии.
- **Результат:** короткое сообщение о восстановленном состоянии и сразу продолжение работы в том же ходе. Меняет код, задачу Backlog.md и `WORKLOG.md` по обычному порядку. Итог — отчёт со статусом «продолжается», «готова к проверке», «готова к ревью», «завершена», «ждёт внешнего условия» или `BLOCKED`.
- **Дальше:** «готова к ревью» — `review-implementation.md` в новой сессии и subagent `reviewer`, если `AGENTS.md` требует второй проход ревью; перед `Done` — subagent `verifier`. «Ждёт внешнего условия» — выполнить условие (например, подключить remote), затем снова `continue-task.md`.

### `implementation-plan.md` — план реализации

- **Когда:** перед STANDARD или LONG задачей, чтобы согласовать план до кода: новая фича, страница, эндпоинт, модель и миграция, изменение и backend, и frontend по одному контракту. Также чтобы актуализировать устаревший план в существующей задаче.
- **Когда не использовать:** SMALL-правка — план не нужен, просто попросите изменение. Баг без подтверждённой причины — сначала `investigate-bug.md` (иначе план получит статус `BLOCKED`). Обновление зависимости — `dependency-upgrade.md`. Агент уже работает над задачей и сам пишет план в задачу — skill `writing-plans`.
- **Как вызвать:** вставить промпт и указать задачу или описание и ограничения.
- **Результат:** план со статусом `READY`, `READY WITH ASSUMPTIONS` или `BLOCKED`, критерии приёмки, шаги со способами проверки, таблица проверок и готовые аргументы Backlog CLI в разделе «Перенос в Backlog.md». Проект, задача и `WORKLOG.md` не меняются.
- **Дальше:** после согласования попросить в той же сессии: «Запиши план в задачу» (или «Создай задачу с этим планом»), затем «Реализуй задачу» или `continue-task.md` в новой сессии.

### `investigate-bug.md` — расследование и исправление бага

- **Когда:** поведение расходится с ожидаемым, причина неизвестна или спорна; нужен доказанный root cause, regression protection и отчёт «до / после».
- **Когда не использовать:** причина очевидна и исправление тривиально — обычная SMALL-правка. Нужен только план исправления с известной причиной — `implementation-plan.md`. Расследование уже начато в прошлой сессии — `continue-task.md` (он продолжит с записанной стадии).
- **Как вызвать:** указать симптом, ожидаемое поведение, воспроизведение и окружение.
- **Результат:** исправление и соразмерная проверка; при неподтверждённой причине — факты, гипотезы и следующий диагностический шаг.
- **Дальше:** для STANDARD и LONG — `review-implementation.md` в новой сессии и subagent `verifier` перед `Done`. Если нужен большой рефакторинг или изменение контракта, промпт останавливается для согласования — затем `implementation-plan.md`.

### `review-implementation.md` — ревью готовой реализации

- **Когда:** реализация одной задачи закончена и нужно решение о приёмке: критерии приёмки, дифф, тесты, архитектурные границы, контракты. Проверяет закоммиченные, staged и unstaged изменения задачи.
- **Когда не использовать:** нужно проверить выполнение плана из нескольких пунктов или находок аудита — `audit-after-changes.md`. Обязательный второй проход ревью по `AGENTS.md` в Claude Code — subagent `reviewer` (изолированный контекст). Быстрая сверка критериев с результатами проверок перед `Done` — subagent `verifier`.
- **Как вызвать:** в новой сессии вставить промпт и дописать: «Задача TASK-15». Если стартовая точка не записана в задаче или `WORKLOG.md` — добавить: «Baseline: `<commit>`».
- **Результат:** таблица критериев со статусами, находки с `Blocks acceptance`, вердикт `READY`, `READY WITH MINOR FINDINGS`, `NOT READY` или `BLOCKED` и список действий перед закрытием задачи. Проект не меняется.
- **Дальше:** `NOT READY` — вернуть находки исполнителю («Исправь [HIGH-1] и [MED-2] из ревью ниже» или `continue-task.md` с вставленным ревью), затем повторить ревью. `READY` — закрытие задачи по `AGENTS.md` («Порядок работы», шаг 7), при необходимости после subagent `reviewer`.

### `audit-after-changes.md` — проверка выполнения плана

- **Когда:** после реализации согласованного плана, списка находок аудита или набора критериев приёмки, особенно если работа шла в нескольких сессиях или подзадачах. Отвечает, выполнен ли план целиком, с базовой точкой, регрессиями и оценкой реализации.
- **Когда не использовать:** нужна приёмка одной задачи с вердиктом по диффу — `review-implementation.md`. Нужен новый поиск проблем по всему проекту — `audit-project.md`.
- **Как вызвать:** в новой сессии вставить промпт и указать объект проверки: «Задача TASK-20 и её подзадачи, baseline `<commit>`» или «Проверь находки [HIGH-1], [MED-2] из аудита ниже» со вставленным отчётом аудита. Если scope менялся по решению пользователя, указать это.
- **Результат:** матрица пунктов со статусами, `VERIFIED mandatory: X / Y`, регрессии `[REG-N]`, оценка реализации 0–100 и вердикт: план выполнен, не выполнен или ждёт внешних условий. Проект не меняется.
- **Дальше:** невыполненные пункты — новая итерация через `continue-task.md` или новую задачу (`implementation-plan.md`). Всё `VERIFIED` — закрытие задачи.

### `audit-project.md` — полный независимый аудит

- **Когда:** периодическая оценка проекта целиком: инженерная основа и готовность к агентской разработке, с находками, приоритетами и баллами. Также повторный аудит после крупной работы, чтобы сравнить баллы.
- **Когда не использовать:** нужно проверить конкретный план или находки прошлого аудита — `audit-after-changes.md`. Нужно ревью одной задачи — `review-implementation.md`.
- **Как вызвать:** в новой сессии вставить промпт. Данные необязательны: «Фокус: права доступа и изоляция данных» сужает глубину, вставленный прошлый аудит используется только как список мест для проверки.
- **Результат:** отчёт с находками `[CRIT-N]`…`[LOW-N]`, false positives, рекомендациями P0–P2 и двумя оценками по 100 баллов. Проект не меняется, отчёт не записывается в репозиторий.
- **Дальше:** выбрать находки для работы; для каждой группы — задача и `implementation-plan.md`; после реализации — `audit-after-changes.md` с Finding IDs.

### `dependency-upgrade.md` — план обновления зависимости

- **Когда не использовать:** общий вопрос о технологии без конкретного обновления («стоит ли переходить с X на Y») — `deep-research.md`. Нужно само обновление по уже согласованному плану — обычная реализация задачи.
- **Результат:** статус `READY`, `READY WITH ASSUMPTIONS` или `BLOCKED`, матрица совместимости, релевантные breaking changes, стратегия, критерии приёмки, план с проверками и откатом, данные для Backlog.md. Проект не меняется.
- **Дальше:** запиши план в задачу, затем реализуй и проверь изменение: `npm run check:agents` и применимые команды по манифестам приложения.

### `deep-research.md` — внешнее исследование

- **Когда:** технический вопрос за пределами репозитория: поведение библиотеки или сервиса, сравнение технологий, спорное утверждение, известные проблемы, подготовка обоснования для ADR.
- **Когда не использовать:** обновление конкретной зависимости проекта — `dependency-upgrade.md`. Вопрос о коде самого проекта — обычный вопрос агенту или `audit-project.md`.
- **Результат:** отчёт с классом источника, степенью подтверждённости и применимостью для каждого существенного утверждения, противоречия, неизвестные, список источников. Проект не меняется; в репозиторий отчёт не записывается.
- **Дальше:** если результат нужен надолго — по отдельной просьбе перенести в ADR, заметки задачи или каноническую страницу `docs/`; для конкретного обновления — `dependency-upgrade.md`; для реализации — `implementation-plan.md`.

### `docs-prompt-generator.md` — генерация промпта для сбора документации

- **Когда:** нужно создать или обновить `collect-docs.md`: снимка нет, он сильно устарел (другая структура, новые области, новые правила документации) или промпт переносится в другой проект. Исследует правила, устройство и классификацию документации, инвентаризирует документы, строит матрицу покрытия и карту системы, затем пишет проектный промпт из постоянной инструкции и снимка на commit.
- **Когда не использовать:** промпт `collect-docs.md` уже есть и актуален — нужно само обновление документации по нему. Нужна оценка проекта целиком — `audit-project.md`.
- **Как вызвать:** в новой сессии вставить промпт целиком. Данные необязательны; критичные вопросы из своей «Фазы 2» (куда писать документацию, язык, читатель, можно ли переписывать устаревшее, куда сохранить промпт, разрешены ли второму агенту docs-линтер и установка зависимостей) промпт задаёт сам одним списком.
- **Результат:** полный текст проектного промпта в ответе; файл сохраняется только по подтверждённому пути (в этом репозитории — `prompts/collect-docs.md`). Генератор среди возможных мест называет `.claude/skills/`, но здесь это генерируемое зеркало, которое не редактируется (`AGENTS.md`, «Инструменты, skills, subagents»). Остальной проект не меняется, команды с побочными эффектами не выполняются.
- **Дальше:** при сохранении — добавить строку и раздел `collect-docs.md` в этот README; затем `collect-docs.md` в новой сессии. Его правки в `docs/agents/` и `prompts/README.md` проходят второй проход ревью (subagent `reviewer`).

### `collect-docs.md` — сбор документации проекта

- **Когда:** документации об устройстве системы нет или она устарела; после существенных изменений кода, конфигурации или деплоя.
- **Когда не использовать:** снимок в Части B сильно устарел (новая структура, другие области) — сначала пересоберите промпт `docs-prompt-generator.md`. Нужна правка правил агентов или процесса — это отдельная задача.
- **Как вызвать:** в новой сессии из корня репозитория вставить промпт целиком; при необходимости дописать области, задачу Backlog.md или каталог черновика (режим черновика, A4).
- **Результат:** новые и исправленные страницы `docs/project/`, точечные правки `README.md` и `frontend/README.md`, задача Backlog.md и отчёт с матрицей покрытия, `TODO: уточнить` и расхождениями.
- **Дальше:** `reviewer` для итогового диффа; затем `adapt-agent-layer.md`.

### `adapt-agent-layer.md` — адаптация агентного слоя под проект

- **Как вызвать:** в новой сессии из корня репозитория вставить промпт целиком. Области исследования можно отдать параллельным исполнителям только на чтение.
- **Результат:** отчёт с предложениями по единому формату (ID, что, зачем, стоимость, приоритет, ADR, критерий приёмки), что не предлагается и вопросы. Проект не меняется.
- **Дальше:** ответ по ID «принять / отклонить / изменить»; по просьбе — задачи Backlog.md; внедрение отдельным поручением с `verifier` и вторым проходом ревью, в конце `audit-after-changes.md` по ID.

| Сценарий                          | Цепочка                                                                                                                                                                         |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Новая фича, страница или эндпоинт | `implementation-plan.md` → «Запиши план в задачу» → реализация (или `continue-task.md` в новой сессии) → `review-implementation.md` → `verifier` → закрытие задачи              |
| Большой план из нескольких задач  | `implementation-plan.md` (LONG, подзадачи) → реализация подзадач с `continue-task.md` → `review-implementation.md` по подзадачам → `audit-after-changes.md` по родительской задаче |
| Баг                               | `investigate-bug.md` → для STANDARD/LONG `review-implementation.md` → `verifier`; при большом исправлении — остановка, затем `implementation-plan.md`                           |
| Передача работы                   | `handoff-compact.md` или `handoff-full.md` в старой сессии → новая сессия: `continue-task.md` + вставленный handoff                                                             |
| Обновление зависимости            | при общем вопросе `deep-research.md` → `dependency-upgrade.md` → задача → реализация → `reviewer` (второй проход обязателен) → `verifier`                                       |
| Аудит и исправления               | `audit-project.md` → выбор находок → задача и `implementation-plan.md` → реализация → `audit-after-changes.md` с Finding IDs                                                    |
| Документация                      | `docs-prompt-generator.md` (если снимка нет или он устарел) → `collect-docs.md` → `reviewer` для правок в `docs/agents/` и `prompts/README.md`                                  |

## Промпт или skill

Skill агент подключает сам внутри репозитория, когда задача совпадает с его описанием; промпт пользователь вставляет вручную, обычно чтобы перенести работу в новый чат или задать разовую задачу с заданным форматом результата. Исключение — skill `handoff`: он помечен как вызываемый только пользователем (`/handoff` в Claude Code), агент не подключает его сам.

- Пауза или передача внутри этого репозитория: контрольная точка в `WORKLOG.md` и заметках задачи Backlog.md (`AGENTS.md`, раздел «Контрольные точки и `WORKLOG.md`»; skill `handoff`).
- Перенос в новый чат: `handoff-compact.md` или `handoff-full.md`. Оба промпта сначала делают ту же контрольную точку, затем выдают текст для копирования.
- Продолжение в новом чате или сессии: `continue-task.md` восстанавливает состояние по протоколу `AGENTS.md` и продолжает работу; вставленный handoff для него — рабочий контекст, который сверяется с репозиторием. Разрешения прошлой сессии (коммиты, push) не переносятся.

Если промпт и skill расходятся, прав `AGENTS.md`; исправляйте промпт или адаптацию skill (`skillAdaptations` в `scripts/sync-agent-skills.mjs`, [инструменты агентов](../docs/agents/tooling.md)).

Баги: `investigate-bug.md` — полный процесс от ожидаемого поведения до доказанного исправления с отчётом, по вашему запросу; skill `systematic-debugging` агент подключает сам по ходу работы. Промпт меняет код и идёт по обычному порядку `AGENTS.md`, поэтому таблица команд «только на чтение» ниже к нему не относится.

План: `implementation-plan.md` — план для согласования без изменений в проекте; строит шаги по порядку из `AGENTS.md` пакетов (собственных skills проекта для эндпоинта, страницы и миграции пока нет) и выдаёт данные для переноса в задачу Backlog.md. Skill `writing-plans` агент подключает сам и пишет план сразу в задачу.

Исследование: `deep-research.md` — общий внешний вопрос (технология, поведение, известные проблемы, сравнение); `dependency-upgrade.md` — конкретное обновление зависимости с учётом lock-файлов и связанных пакетов проекта. Результат исследования — пересказ: в репозиторий он попадает только через ADR, задачу Backlog.md или каноническую документацию.

Проверки и ревью:

- `audit-project.md` — полный независимый аудит по вашему запросу;
- `audit-after-changes.md` — полная независимая проверка, выполнен ли согласованный план или набор находок аудита, с базовой точкой, регрессиями и оценкой реализации;
- `review-implementation.md` — ревью готовой реализации одной задачи: критерии приёмки, дифф, тесты, требования к реализации из `AGENTS.md` и вердикт о приёмке (закрытие задачи — после ревью);
- subagent `verifier` (`.claude/agents/verifier.md`) — быстрая сверка критериев приёмки с результатами проверок перед переводом задачи в `Done`;
- subagent `reviewer` (`.claude/agents/reviewer.md`) — второй проход ревью диффа по `AGENTS.md`, который `AGENTS.md` требует для зависимостей, сборки, CI, моделей и миграций, аутентификации и прав доступа, инструкций агентов, hooks и кода безопасности.

Subagents определены для Claude Code; другой агент может выполнить их текст в отдельной сессии ([инструменты агентов](../docs/agents/tooling.md)).

Оба промпта проверки используют одни и те же статусы критериев: `VERIFIED`, `IMPLEMENTED, NOT VERIFIED`, `PARTIAL`, `NOT IMPLEMENTED`, `NO LONGER APPLICABLE`, `REJECTED / INTENTIONALLY NOT DONE`.
