# Исследование и план обновления зависимости

Исследуй обновление указанной зависимости или согласованной группы зависимостей и подготовь **безопасный implementation-ready план обновления без внесения изменений в проект**.

Главная цель:

> Установить фактическое текущее состояние зависимости в проекте, определить подходящую target version, изучить официальные breaking changes и требования совместимости, проверить влияние на связанные зависимости и архитектуру проекта, затем составить минимальный проверяемый план upgrade и rollback.

Этот промпт — **исследование и planning**. **Не выполняй обновление.** Результат — план для переноса в задачу Backlog.md по `AGENTS.md`.

---

## 1. Режим работы



Какие скрипты проекта безопасны — раздел «Команды для проверок только на чтение» [`prompts/README.md`](README.md). Не считай команду безопасной по имени (`check`, `test`, `build`, `outdated`, `tree`): сначала установи, что она делает. Полезную, но потенциально изменяющую проверку не запускай — включи её в verification plan и отметь, что во время исследования она не выполнялась.

### Инструменты исследования

| Что узнать                                                      | Инструмент                                                                                                                                                                                 | Заметки                                                                                   |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| документация, migration guide, changelog                        | context7 (MCP-инструменты или skill `context7-cli`), официальный сайт и репозиторий                                                                                                        | **сеть**                                                                                  |
| где проект использует API пакета                                | `rg`, `grep`, поиск по коду                                                                                                                                                                | только чтение                                                                             |

Lock-файлы не читай целиком: цель — установить resolved versions и граф зависимостей точечным поиском, а не загрузить файл в контекст.

Если сети нет, а нужные сведения не лежат в репозитории и не даны пользователем, исследование `BLOCKED` (раздел 5).

### Секреты

Не включай в результат значения токенов, ключей, cookie, содержимого `.env*`, `.npmrc` с авторизацией и персональные данные — только тип и путь.

## 3. Предмет обновления

```text
Dependency:
Declared specifier:
Resolved version(s):
Target version:
Upgrade type: patch / minor / major / unknown
Dependency relation(s): direct / transitive / peer-only
Dependency scope(s): production / development / optional
Role(s): runtime / build / test / lint / generation / infrastructure / other
Reason: security / compatibility / feature / maintenance / requested / other
```



**Граф зависимостей**: direct или transitive; где объявлена; кто импортирует; какие конфигурации используют; peer и optional dependencies; ограничения package manager; роль в runtime или сборке; generated output и тестовая инфраструктура, которые от неё зависят. Не ограничивайся строкой в манифесте.

**Несколько манифестов и версий**: корневой package.json обслуживает агентский слой. pom.xml, Maven Wrapper и frontend/package.json проверяй только при наличии. Для каждого потребителя фиксируй объявленную и разрешённую версию, совместимость и роль.

## 5. Внешние источники


**Evidence соответствует target version**: оно относится к выбранной версии или к диапазону, который явно её включает. Требования документации последней версии не переносятся автоматически на более старую.

**Если необходимого авторитетного evidence недостаточно** — `Research status: BLOCKED`, когда без него нельзя надёжно выбрать target version, подтвердить совместимость, установить применимые breaking changes или определить безопасный путь миграции.

Отсутствие отдельного migration guide само по себе не блокирует исследование, если нужные факты достаточно подтверждаются другими первичными источниками: release notes, changelog, официальной документацией, метаданными пакета (для patch- и многих minor-обновлений migration guide не существует). Память модели не заменяет необходимое авторитетное evidence. Если нужные материалы уже в репозитории или даны пользователем, отсутствие сети не блокирует.

### Известные проблемы target version

| Статус           | Когда                                                                                                                   |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `CONFIRMED`      | признана maintainers, документирована в release note, advisory или исправлении, либо воспроизводится в условиях проекта |
| `REPORTED`       | есть релевантный issue, но причина или применимость к проекту не подтверждены                                           |
| `NOT APPLICABLE` | подтверждена, но условия проекта ей не соответствуют                                                                    |
| `UNCERTAIN`      | evidence недостаточно                                                                                                   |

Один открытый issue — не доказательство регрессии.

## 6. Target version и совместимость



**Peer-экосистема**: для каждого связанного пакета (плагин, адаптер, интеграция с фреймворком или тестами, пакет типов):

```text
Package:
Current:
Required / supported by target:
Status: YES / NO / UNCERTAIN
```

Ищи: ядро обновлено, а плагин не поддерживает target; плагин требует другой major; peer-диапазон формально допускает версию, но документация сообщает ограничение; типы рассинхронизированы; инструмент использует внутренний API. Пакеты, которые должны меняться вместе, планируй как одну группу совместимости.

## 7. Влияние на проект

**Breaking changes** — только релевантные проекту, для промежутка `resolved version(s) → target`:

```text
Breaking change:
Introduced in:
Project affected: YES / NO / POSSIBLY
Evidence: path / symbol / config
Required action:
```

**Использование затронутых API** (удалены, deprecated, изменили сигнатуру, умолчания, семантику, имя или формат конфигурации) — по реальным путям и symbols: `CONFIRMED` (используется), `NOT USED` (в релевантной области не найдено), `UNCERTAIN`. Не планируй миграцию API, которого проект не использует.

**Изменение умолчаний и поведения** — особенно опасно, потому что компилируется без ошибок: новые или удалённые умолчания, более строгая валидация, кэширование, планирование, сериализация, разрешение путей, tree-shaking, разбиение кода, тестовое окружение, поведение в браузере, обработка ошибок, умолчания безопасности. Применимое изменение требует проверки в рантайме или регрессионного теста.

## 8. Security upgrades

Проверь официальный advisory, затронутый диапазон и версии с исправлением; попадает ли текущая разрешённая версия (из lock-файла) в затронутый диапазон; доказана ли достижимость уязвимого кода из приложения; есть ли обходной путь; требует ли исправление major; остаются ли уязвимые транзитивные версии после обновления.

Отсутствие найденного пути к уязвимому коду не доказывает отсутствие эксплуатируемости. Наличие CVE не доказывает эксплуатируемость в этом проекте. Но неподтверждённая эксплуатируемость не отменяет обновление, если его требует политика безопасности.

Порядок: advisory → затронутые разрешённые версии → версии с исправлением → совместимость → минимальная безопасная target → проверка. Если есть безопасное исправление в patch или minor, не планируй major только потому, что он новее; не расширяй security-обновление до модернизации проекта.

## 9. Scope и стратегия

Не обновляй «весь стек заодно». Каждая дополнительная зависимость требует конкретной причины: peer-совместимость, требование миграции, безопасность, официальный путь обновления, прямая техническая зависимость. Остальное — в `Out of scope` (`AGENTS.md`: не обновляйте посторонние пакеты).

| Стратегия                                                         | Когда                                            |
| ----------------------------------------------------------------- | ------------------------------------------------ |
| **Direct** `current → target`                                     | миграция проста, совместимость подтверждена      |
| **Staged** `current → подготовка → промежуточная версия → target` | этого требует официальный путь или профиль риска |
| **Coordinated** `пакет A + плагин B + адаптер C`                  | версии должны меняться вместе                    |

Если ни одну безопасную стратегию определить нельзя (target несовместим со стеком, нет совместимого peer, путь миграции неясен, авторитетные данные противоречивы или недостаточны, нужно архитектурное решение) — это не стратегия, а итог исследования: `Research status: BLOCKED` (раздел 11). Не выдумывай обходной путь ради `READY`.

**Несколько зависимостей**: если они образуют группу совместимости, не составляй независимые планы — постройте связь (`пакет A → плагин B, адаптер C, типы D`), выбери совместимый набор версий и порядок, минимизирующий промежуточно сломанные состояния. Независимые пакеты раздели на отдельные единицы обновления.

**«Обнови до latest»** — не разрешение слепо поставить последний релиз: установи latest stable, проверь требования, peers, breaking changes, стек и известные проблемы, и только затем решай. Если latest несовместим — укажи latest stable, latest compatible и причину.

## 10. План реализации


Шаги для любого изменения зависимостей делятся на две группы.

**Требования `AGENTS.md`** — снимок на момент написания промпта. Перед составлением плана сверь его с актуальным `AGENTS.md` (разделы «Команды и проверка», «Зависимости», «Второй проход ревью»); при расхождении действует `AGENTS.md`:

- перед изменением проверены актуальная документация и совместимость (это исследование); посторонние пакеты не обновляются;
- финальные проверки: `npm run check:agents` и применимые команды Maven и frontend по существующим манифестам;
- **второй проход ревью** итогового диффа; собственная проверка исполнителя его не заменяет;
- причина добавления или обновления каждой зависимости указана в отчёте (и в итоге задачи).

**Практика этого проекта** — не правила `AGENTS.md`, а проверки, которые на опыте ловят проблемы обновлений:

- выполнены пункты связок из раздела 4, относящихся к обновляемым пакетам;

**Acceptance criteria** выводи из конкретного исследования: какие версии должны разрешиться, какие breaking changes мигрированы, какое поведение и какие контракты должны сохраниться, какие проверки должны пройти. Каждый критерий проверяем и связан с проверкой в verification plan. Не используй пример из шаблона ответа как универсальный список.

**Verification** связывай с конкретными рисками обновления и критериями приёмки, а не пиши «запустить тесты»:

```text
Verification: соответствующий тест и воспроизводимый сценарий подтверждают сохранение затронутого контракта.
```

**Rollback** затрагивает **только изменения обновления**: revert изолированного коммита обновления, обратное изменение только его файлов и hunks, возврат прежних specifiers и resolutions, обратная миграция только его конфигурации и кода. Не через `git reset --hard`, массовый `checkout` или `restore` и не через восстановление всего грязного worktree. Для рискованных обновлений проверь миграцию данных или конфигурации, изменение сохраняемого состояния и generated contracts, необратимые шаги, возможность разбить обновление на обратимые контрольные точки. Если откат тривиален — хватит короткого описания.

## 11. Статус исследования

| Статус                     | Когда                                                                                                                                                                                                                                                                        |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **READY**                  | target обоснована, совместимость подтверждена, существенных неизвестностей нет, стратегия определена                                                                                                                                                                         |
| **READY WITH ASSUMPTIONS** | остались только локальные обратимые предположения, которые безопасно подтвердить при реализации и которые не влияют на архитектуру, публичные контракты, безопасность и стратегию миграции                                                                                   |
| **BLOCKED**                | без дополнительного решения или авторитетного evidence нельзя безопасно выбрать target или план: нет совместимого peer, неясна поддержка версии фреймворка, migration guide не покрывает используемое API, несовместим runtime, нет доступа к release и migration информации |

# Инварианты

1. **Сначала исследование совместимости, потом план; во время промпта зависимости и проект не меняются.**
2. **Объявленная (declared) и разрешённая (resolved) версии — разные факты; при нескольких версиях нет единственной «текущей версии».**
3. **Target выбирается по совместимости и требованиям, а не по `latest`; evidence относится к выбранной версии и подтверждено авторитетным источником, иначе — `BLOCKED`.**
4. **Связанные зависимости этого проекта берутся из раздела 4 и фактической конфигурации; peer-пакеты проверяются как граф совместимости.**
5. **Открытый issue — `REPORTED`, а не доказанная регрессия; breaking changes сопоставляются с фактическим использованием.**
6. **Изменение умолчаний — потенциально ломающее поведение даже без ошибки компиляции.**
7. **Не обновляй соседние зависимости без доказанной необходимости.**
8. **План включает актуальные обязательные шаги для изменения зависимостей из `AGENTS.md`; не полагайся на зафиксированный в промпте список, если правила проекта изменились.**
9. **Acceptance criteria выводятся из исследования и входят в результат; каждый критерий и риск связан с проверкой; rollback затрагивает только изменения обновления.**
10. **Новый major сам по себе не требует ADR.**
11. **Если совместимость нельзя доказать — `BLOCKED` лучше speculative upgrade.**
