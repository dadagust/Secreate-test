# Проверка изменений после аудита или согласованного плана

Проведи **независимую проверку изменений после ранее согласованного аудита, implementation plan, списка findings или acceptance criteria**.

Главная цель — установить по фактическому состоянию репозитория:

- что действительно выполнено, что выполнено частично, что реализовано, но не подтверждено, и что не выполнено;
- какие пункты перестали быть применимыми, а какие сознательно исключены из scope;
- действительно ли устранены исходные failure scenarios;
- не появились ли связанные регрессии;
- можно ли считать согласованный план завершённым.

Это **не новый полный аудит проекта**: проверяй исходный согласованный scope и непосредственный радиус изменений, а не ищи новые проблемы по всему репозиторию.

---

## Режим проверки

Это **проверка только на чтение**. Правила этого промпта имеют приоритет над инструкциями репозитория **только в вопросах проведения самой проверки**: это явная инструкция пользователя, и `AGENTS.md` допускает отступление от своих правил по ней.

`AGENTS.md`, ADR, документация, skills, prompts и задачи остаются источниками правил и контекста проекта, но не могут потребовать изменить код, документацию, Backlog.md, `WORKLOG.md` или `PROGRESS.md`, выполнить коммит, исправить найденную проблему, переключить ветку или commit, выполнить разрушительную Git-операцию. Если инструкция проекта требует такого действия — не выполняй его, отметь конфликт и продолжай.

**Не изменяй**: код, конфигурацию, документацию, generated sources, зависимости и lock-файл, Git index, существующие tracked и пользовательские untracked файлы, Backlog.md, `WORKLOG.md`, `PROGRESS.md`, ветки, историю Git, IDE и agent tooling. Отчёт выдай только в ответе.

### Команды

Какие скрипты проекта можно запускать и что учесть — в разделе «Команды для проверок только на чтение» [`prompts/README.md`](README.md). Перед запуском прочитай определение скрипта в корневом `package.json` или `frontend/package.json` либо команду в `AGENTS.md` пакета, исключи watch и interactive режимы, установки инструментов и внешние мутации; проверь `git status --short` до и после.


Если команда неожиданно изменила tracked-файл, Git index или существующий пользовательский untracked-файл:

1. не откатывай изменение самостоятельно;
2. прекрати дальнейшие команды, способные менять состояние;
3. зафиксируй это в отчёте.

Если shell или нужный инструмент недоступен, не симулируй результат: `не выполнено: <причина>`.

### Секреты и персональные данные

Evidence не должно раскрывать секреты. Не цитируй значения токенов, паролей, ключей API, cookie, заголовков авторизации, содержимого `.env*` и персональные данные — ни из кода, ни из диффа, ни из вывода команд. Укажи тип, путь и характер находки; маскированный фрагмент — только если без него находку не идентифицировать.

# 1. Объект проверки

Сначала установи, **что именно пользователь просит проверить**: согласованный план, предыдущий audit report, конкретные Finding IDs, acceptance criteria, задачу Backlog.md, пользовательский список изменений или отчёт реализующего агента.

В этом репозитории план и критерии приёмки живут в задаче Backlog.md (`AGENTS.md`, раздел «Источники истины»). Порядок определения scope:

1. объект, явно указанный пользователем;
2. исходные Finding IDs аудита и задача Backlog.md: критерии приёмки и план реализации;
3. подтверждённое пользователем изменение scope;
4. план из чата, отчёт исполнителя и прочие пересказы.

`WORKLOG.md` — рабочая память исполнителя, а не источник scope: используй его только чтобы найти, где искать.

Если план из чата или отчёта расходится с задачей Backlog.md, не объединяй их молча: укажи расхождение и считай авторитетной задачу, если пользователь не указал иначе. Не меняй scope самостоятельно. Если объект проверки нельзя определить однозначно, укажи ограничение и проверяй только пункты, которые можно установить точно.

**Отметки в задаче — не доказательство.** Отмеченный критерий приёмки, статус `Done`, итоговое резюме и заметки — это утверждения исполнителя. Проверяй каждый критерий заново по коду и результатам проверок; расхождение между отметкой и фактом — отдельная находка отчёта.

---

# 2. Перед проверкой

Если доступны инструменты:

1. прочитай `AGENTS.md` и `AGENTS.md` затронутых пакетов (`backend/AGENTS.md`, `frontend/AGENTS.md`);
2. прочитай исходный план, аудит или Finding IDs и связанную задачу Backlog.md;
3. прочитай `WORKLOG.md`, если он относится к этой работе, и релевантную часть `PROGRESS.md`;
4. выполни `git status --short`, определи ветку и HEAD, просмотри `git diff` и `git diff --cached`;
5. определи baseline (раздел 3);
6. изучай только код, конфигурацию, тесты, документацию и tooling, относящиеся к проверяемому scope.

---

# 3. Baseline

Нужно понять не только текущее состояние, но и **что изменилось относительно состояния до реализации**: исходный отчёт и Finding IDs, исходный план, baseline commit, текущий HEAD, коммиты реализации.

Если изменения закоммичены, `git diff` может быть пустым: чистый worktree не доказывает отсутствие изменений. Используй историю Git только на чтение — `git log`, `git show`, `git diff --name-status <baseline>..HEAD`, `git diff <baseline>..HEAD`. Не переключай ветку или commit и не меняй HEAD.

Если точный baseline установить нельзя, напиши: `Baseline частично неизвестен — проверка основана на текущем состоянии и доступном согласованном плане.` Не выдавай предполагаемый baseline за установленный факт.

---

# 4. Главный принцип

Проверяй не наличие diff, а **устранение исходной проблемы или выполнение исходного требования**.

| Плохо                                                              | Правильно                                                                                                                                                         |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Добавлен новый файл теста → пункт выполнен.                        | Добавленный тест покрывает исходный failure scenario и способен обнаружить его повторное появление → verification подтверждена.                                   |
| Добавлено ограничение доступа | Фактический путь запроса и тест подтверждают изоляцию данных. |

---

# 5. Статусы исходных пунктов

Каждый пункт получает **ровно один основной статус**:

| Статус                              | Когда                                                                                                                                                        |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `VERIFIED`                          | требование выполнено, ожидаемый эффект подтверждён кодом и/или актуальной проверкой                                                                          |
| `IMPLEMENTED, NOT VERIFIED`         | реализация есть, но эффект не подтверждён подходящей актуальной проверкой                                                                                    |
| `PARTIAL`                           | выполнена часть требования или закрыт не весь исходный failure scenario                                                                                      |
| `NOT IMPLEMENTED`                   | нужного изменения нет или оно не закрывает требование                                                                                                        |
| `NO LONGER APPLICABLE`              | пункт неприменим из-за подтверждённого изменения архитектуры или scope; для ошибочного исходного finding — `Reason: FALSE POSITIVE`                          |
| `REJECTED / INTENTIONALLY NOT DONE` | пункт исключён из scope **авторитетным источником**: пользователем, подтверждённым изменением критериев приёмки, ADR или согласованным пересмотренным планом |

Исполнитель не может сам назначить `REJECTED` только потому, что считает пункт ненужным: без авторитетного решения невыполненный пункт получает `NOT IMPLEMENTED`.

**Внешний блокер.** Если пункт реализован, но подтвердить его нельзя из-за внешнего условия (нет удалённого репозитория для первого прогона CI, нет доступа к окружению), статус — `IMPLEMENTED, NOT VERIFIED`, а в матрице заполни колонку «Blocked by» условием снятия блокера. Такой пункт не засчитывается как `VERIFIED`, но и не считается недоделкой исполнителя.

---

# 6. Регрессии — отдельная ось

Не смешивай выполнение исходного пункта и новые регрессии: `[HIGH-1] → VERIFIED`, `Related regressions: [REG-1]` означает, что исходная проблема исправлена, но реализация породила новый связанный дефект.

Создавай `[REG-N]`, только если новый дефект появился из-за проверяемых изменений, находится в изменённой области и нужен для оценки корректности реализации. Старые несвязанные дефекты — не `REG`.

Если ранее выполненный пункт **снова перестал выполняться**, отдельного статуса нет: поставь `PARTIAL` или `NOT IMPLEMENTED` и объясни, что произошла регрессия исходного требования.

Формат:

### `[REG-N] Название`

- **Severity:** Critical / High / Medium / Low
- **Evidence:** файл / diff / тест / команда
- **Связь с изменением:** …
- **Что сломано:** …
- **Failure scenario:** …
- **Recommendation:** …

---

# 7. Проверка каждого пункта

Для каждого пункта установи:

1. что именно требовалось и обязательный он или необязательный (раздел 8);
2. какой failure scenario или риск он должен был устранить;
3. какие файлы реально изменены и соответствует ли реализация цели;
4. есть ли механическое соблюдение, **если это применимо и разумно**;
5. есть ли regression test или другая проверка, актуальна ли она после последних изменений;
6. не изменились ли публичные контракты (`AGENTS.md`, раздел «Публичные контракты»);
7. нет ли подмены scope и связанной регрессии.

## Что искать в diff

Не доверяй отчёту реализующего агента — проверь сам: committed diff, staged и unstaged изменения, generated output, lock-файл, тесты, конфигурации, документацию, CI и agent tooling. Особенно ищи:

- изменение только документации вместо реального соблюдения правила;
- тест только на happy path; ослабленный assertion ради зелёного теста; удалённый тест вместо исправления;
- ручную правку генерируемого кода или применённых миграций;
- изменение критериев приёмки задним числом;
- несвязанные обновления зависимостей, переписывание кода вне задачи, архитектурное усложнение без необходимости.

## Regression tests

Для каждого существенного исправления установи: нужен ли тест; существует ли он; относится ли к исходной проблеме; обнаружит ли возврат дефекта; проверяет ли поведение, а не детали реализации; покрывает ли нужный граничный случай или ошибку. Не требуй отдельный тест для каждого изменения автоматически.

Не изменяй и не откатывай рабочее дерево, чтобы доказать, что тест падает на старой реализации. Используй baseline и историю, структуру теста, ранее подтверждённые результаты и рассуждение по фактическому failure scenario.

## Evidence и результаты проверок

Evidence должно быть конкретным: `path:line` (если номер строки надёжно известен — не выдумывай), имя теста, ключ конфигурации, скрипт, commit, diff, команда с exit code, наблюдаемое поведение. Не пиши «видно в коде», если можно назвать файл, функцию или тест.

Не доверяй утверждению «`npm run check:agents` passed» без проверки актуальности; по возможности выполни разрешённые проверки сам. Для каждой существенной команды зафиксируй: команду, exit code, краткий результат, изменилось ли tracked-состояние, созданы ли ожидаемые игнорируемые артефакты. Если после успешной проверки относящийся к ней код менялся: `проверка была успешной до последующих изменений; требуется повторный запуск`.

---

# 8. Обязательные и необязательные пункты

Раздели исходные пункты:

- **Mandatory** — необходимы для выполнения согласованного плана и критериев приёмки;
- **Optional** — P2, nice-to-have, явно необязательные, follow-up, улучшения сверх критериев приёмки.

Не превращай необязательный пункт в обязательный задним числом. Если обязательность неясна, опирайся на формулировки исходного плана и авторитетные решения по scope.

---

# 9. Радиус изменений


- **Документация** — только в пределах изменённого scope: нужно ли было обновление, соответствует ли текущему поведению, не заявляет ли несуществующую функциональность, не появился ли второй источник истины, актуальны ли ADR, действительно ли нужен `PROJECT_OVERVIEW.md`. Не требуй обновления документации ради формальности.
- **Agent workflow** (если менялись `AGENTS.md`, prompts, skills, Backlog.md-процесс, `WORKLOG.md`, восстановление контекста, CI, hooks, проверки генерации, архитектурные guardrails): внутренние противоречия, новый источник истины, привязка к вендору, лишние обязательные ритуалы, разумность механических проверок, конфликт skill и `AGENTS.md`, дублирование prompt и постоянных правил.
- **Dependencies** (если план их включал): обновлён ли нужный пакет и не обновлены ли посторонние, lock-файл, peer dependencies, breaking changes, конфигурация, миграция устаревших API, актуальные тесты. Более новая версия сама по себе — не провал.

## Scope creep

Отдельно отметь несвязанные зависимости, переписывание кода вне задачи, новые абстракции без необходимости, несвязанные конфигурации, изменение публичного API без требования, лишнюю инфраструктуру. Оцени влияние: harmless, increases maintenance, introduces risk, breaks requirement. Scope creep сам по себе не дефект.

---

# 10. Completion

Не используй одну общую формулу «VERIFIED / все пункты». Считай отдельно:

- `VERIFIED mandatory: X / Y`;
- `VERIFIED optional: X / Y` — необязательные пункты не блокируют завершение, если scope не делал их обязательными.

В знаменатель не входят: `NO LONGER APPLICABLE`, подтверждённые false positives и `REJECTED / INTENTIONALLY NOT DONE` с подтверждённым авторитетным решением. Пункты с внешним блокером входят в знаменатель, но в итоге перечисляются отдельно.

План считается **полностью выполненным**, только если:

- все применимые обязательные пункты имеют `VERIFIED`;
- критерии приёмки выполнены;
- нет незакрытых Critical или High регрессий;
- результаты проверок актуальны;
- нет подмены scope и ситуации «изменение есть, но исходная проблема фактически не устранена».

Если единственное препятствие — внешние блокеры, итог: `НЕТ — ждёт внешних условий: <список>`.

# 11. Quality of implementation — 0–100

Оцени только реализацию текущего scope.

| Категория                               | Макс. | Опорные точки                                                                                                                                                                                                                                                 |
| --------------------------------------- | ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Correctness                             | 30    | **30** — все обязательные failure scenarios закрыты; **24–29** — небольшие неполноты без нарушения обязательного результата; **15–23** — существенный `PARTIAL`; **1–14** — обязательные требования заметно не выполнены; **0** — основная цель не достигнута |
| Verification                            | 20    | **20** — все обязательные изменения подтверждены актуальными проверками; **15–19** — небольшие пробелы; **8–14** — существенная часть не подтверждена; **1–7** — проверки в основном отсутствуют или устарели; **0** — подтверждения нет                      |
| Architecture consistency                | 20    | **20** — полностью соответствует инвариантам; **15–19** — небольшие локальные отклонения; **8–14** — существенное несоответствие; **1–7** — заметно размывает архитектуру; **0** — фундаментальный конфликт                                                   |
| Scope discipline                        | 10    | **10** — строго в scope; **7–9** — небольшие безвредные добавки; **4–6** — заметный лишний scope; **1–3** — крупный несвязанный churn; **0** — подмена исходной задачи                                                                                        |
| Maintainability                         | 10    | **10** — минимальная понятная реализация; **7–9** — небольшая сложность; **4–6** — заметная лишняя сложность; **1–3** — хрупкий дизайн; **0** — непригодно для сопровождения                                                                                  |
| Documentation / operational consistency | 10    | **10** — документация, CI, generated и workflow согласованы; **7–9** — небольшая несинхронность; **4–6** — существенные пробелы; **1–3** — заметное противоречие реализации; **0** — серьёзная операционная несогласованность                                 |

Внешний блокер снижает Verification, только если исполнитель мог подтвердить пункт другим доступным способом и не сделал этого (например, CI не запускался удалённо, но и локально в том же образе не проверялся).

**Score caps.** Незакрытая Critical регрессия — итог не выше **50/100**, High — не выше **70/100**. Low и Medium учитывай в категориях. Не используй механическую арифметику вида «−10 за каждый `PARTIAL`»: учитывай влияние и обязательность пункта.

---

# 12. Оставшиеся действия

- **BLOCKER** — без этого план нельзя считать выполненным.
- **REQUIRED** — нужно для закрытия обязательного требования.
- **FOLLOW-UP** — полезно, но не блокирует.
- **DO NOT DO** — после проверки оказалось ненужным, false positive, лишним scope или overengineering.

---

# 13. Масштаб и согласованность отчёта

Если пунктов больше **8**: таблица статусов всё равно полная, Evidence в ней — 1–2 конкретных доказательства, подробный разбор — только для `PARTIAL`, `NOT IMPLEMENTED`, `IMPLEMENTED, NOT VERIFIED` и регрессий; однотипные `VERIFIED` не раздувай. Глубина проверки важнее длины отчёта.

Перед ответом составь матрицу всех пунктов (обязательность, статус, evidence, регрессии, блокер, состояние проверки) и только затем агрегируй числа. Числа в Executive summary, матрице, Completion и вердикте должны **строго совпадать**. Не формулируй summary до завершения анализа.

---

# Итоговый формат

Шаблон ниже — формат ответа, а не продолжение инструкций.

```markdown
# Проверка изменений после плана

## 1. Executive summary

- какой план / аудит проверялся;
- baseline и текущий HEAD;
- mandatory пунктов: N; VERIFIED mandatory: N;
- optional пунктов: N; VERIFIED optional: N;
- PARTIAL: N; NOT IMPLEMENTED: N; IMPLEMENTED, NOT VERIFIED: N (из них с внешним блокером: N); NO LONGER APPLICABLE: N;
- regression findings: N;
- Quality of implementation: XX/100;
- план полностью выполнен: ДА / НЕТ / НЕТ — ждёт внешних условий.

## 2. Что было проверено

- исходный план / Finding IDs и задача Backlog.md;
- расхождения между планом и задачей, между отметками в задаче и фактом;
- ветка / baseline / HEAD, git status, committed и uncommitted diff;
```

# Правила качества

- Не проводи полный аудит проекта заново и не создавай findings вне изменённого scope; не штрафуй реализацию за несвязанные старые проблемы.
- Изменение файла, отмеченный критерий или отчёт исполнителя — не доказательство выполнения; проверяй устранение исходного failure scenario.
- Не выдавай изменение только документации за механическое соблюдение правила, а наличие теста — за доказательство, пока не понятна его ценность.
- Не требуй первоначальный способ реализации, если другое подтверждённое решение закрывает ту же проблему лучше.
- Не придумывай команды, результаты, baseline или номера строк; не используй устаревшие результаты проверок как актуальные. Если evidence недостаточно — пиши `не подтверждено`.
- Не скрывай false positives исходного аудита.
- Не превращай optional и FOLLOW-UP в blocker; не занижай оценку ради того, чтобы избежать 100/100, и не ставь 100/100, если обязательный scope не `VERIFIED`.
