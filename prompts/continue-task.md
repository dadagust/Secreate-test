# Продолжение незавершённой задачи

Восстанови состояние текущей незавершённой задачи по репозиторию и **продолжи работу с правильной точки**, не заставляя пользователя повторять контекст и не выполняя заново уже завершённые шаги.

Главная цель:

> Восстановить фактическое состояние задачи из Backlog.md, `WORKLOG.md`, Git и текущего кода, выявить расхождения и, когда project workflow это однозначно допускает, согласовать canonical task state с фактическим repository state, определить ближайший незавершённый шаг и продолжить реализацию.

Это **не новый planning session** и не новый source of truth. Если у задачи есть актуальный план в Backlog.md — продолжай по нему. Не создавай `TASK_PLAN.md`, `CONTINUE.md`, `HANDOFF.md`, `SESSION_STATE.md` и другие конкурирующие файлы состояния.

---

## 1. Текущая инструкция пользователя и прошлый контекст

Текущая явная инструкция пользователя — **актуальное ограничение текущей работы**, а не historical chat context. Она может уточнять, какую задачу продолжать, текущий scope, что делать и чего не делать, дополнительные ограничения и точку продолжения. Учитывай её вместе с repository evidence и обязательными правилами проекта. Если она противоречит `AGENTS.md`, действующему ADR или обязательному контракту — не выбирай сторону молча: зафиксируй конфликт и не выполняй небезопасное действие.

Старые chat summaries, memories и сообщения прошлых агентов — только вспомогательное historical evidence.

**Handoff.** Если пользователь вставил результат `handoff-compact.md` или `handoff-full.md`, это рабочий контекст, а не источник истины: сверь его с репозиторием, как требует инструкция в самом handoff. При расхождении прав репозиторий, а новые сообщения пользователя важнее handoff.

**Разрешения не переносятся.** Разрешение на коммиты (в том числе checkpoint-коммиты), push и другие действия, требующие явного согласия по `AGENTS.md` (раздел «Git»), действует, только если пользователь дал его **в текущей сессии**. Запись о разрешении в handoff, `WORKLOG.md`, заметках задачи или старом чате разрешением не является. Без него работай без коммитов; push, force-операции и переписывание истории — только по явному запросу.

---

## 2. Протокол восстановления

Следуй разделу «Восстановление контекста» `AGENTS.md` — это обязательный порядок, а не рекомендация:

1. `AGENTS.md` и применимые вложенные `AGENTS.md` → `PROJECT_OVERVIEW.md` → `PROGRESS.md`;
2. активная задача: `npm run backlog -- task list -s "In Progress" --plain`, затем `npm run backlog -- task view <id> --plain`;
3. `WORKLOG.md`, если его строка `Task:` совпадает с id активной задачи;
4. `git status`, `git diff`, `git diff --cached`;
5. `AGENTS.md` пакета (`backend/AGENTS.md`, `frontend/AGENTS.md`), документация, ADR, код и тесты, относящиеся к следующему шагу.

Большие документы и ADR читай в части, относящейся к задаче. Hook `SessionStart` в Claude Code выводит активные задачи, строку `Task:` и `git status` — это подсказка, а не замена протоколу.

Учитывай из `AGENTS.md`: уровень задачи, работу с Backlog.md и `WORKLOG.md`, требования к проверкам, контрольные точки, правила документации и ADR, безопасность Git, обязательный второй проход ревью.

---

## 3. Найди текущую задачу

Прочитай задачу полностью: цель, критерии приёмки, scope, план реализации, заметки и контрольные точки, зависимости, подзадачи для LONG, записанные результаты.

### Одна активная задача

Считай её **основным кандидатом**, но подтверди identity: строка `Task:` в `WORKLOG.md` совпадает или журнала нет; Git state и существенный diff не противоречат её scope; последние заметки соответствуют фактическому состоянию. Если есть явное противоречие — сначала сверка (раздел 7). Не продолжай задачу автоматически только потому, что она единственная в `In Progress`.

### Несколько активных задач

Если пользователь в текущей инструкции назвал задачу — продолжай её. Иначе **спроси, какую продолжать** (`AGENTS.md`, «Восстановление контекста»): перечисли кандидатов и то, что указывает на каждого (`WORKLOG.md`, diff, ветка, заметки). До ответа проект не изменяй.

### Активной задачи нет

Проверь `WORKLOG.md`, Git state и последние релевантные задачи Backlog.md. Если незавершённая STANDARD/LONG работа фактически есть, но задача не в `In Progress`, сначала установи identity существующей задачи. Исправляй учёт задачи сам, только если identity однозначна, изменение прямо следует из `AGENTS.md` и порядка работы с Backlog.md и не требует нового решения о scope, владельце или намерении. Не создавай задачу на основании догадки, не переоткрывай завершённую без однозначного evidence, не меняй владельца и статус произвольно.

Если `WORKLOG.md` указывает на задачу, которая уже в `Done`, сначала проверь текущую инструкцию пользователя:

- если пользователь не просит продолжить, доделать или перепроверить эту задачу — действуй по `docs/agents/context-recovery.md`: перенеси необходимые результаты в задачу и документацию, затем верни журнал к шаблону;
- если текущая инструкция снова делает эту задачу актуальной («там надо доделать X») — сначала проведи сверку (раздел 7) и не очищай полезный рабочий контекст автоматически. Статус задачи сам не меняй: вернуть её в работу или завести новую — решение по порядку работы с Backlog.md, а при неясности — вопрос пользователю.

Чужую незавершённую задачу в `WORKLOG.md` не затирай — спроси пользователя.

## 4. `WORKLOG.md` и Git state

**`WORKLOG.md`** относящейся задачи — **working memory незавершённой работы**, а не source of truth реализации. Извлеки: последнюю контрольную точку, что сделано и проверено, что осталось, блокеры, ожидаемый следующий шаг, незавершённые эксперименты, записанные процессы и окружение. Журнал другой задачи с текущей не смешивай.

**Git state** зафиксируй до любых изменений:

```bash
git status --short --branch
git rev-parse HEAD
git diff --name-status
git diff --cached --name-status
```

Полный diff читай только для релевантных путей (`git diff -- <paths>`, `git diff --cached -- <paths>`); при необходимости используй историю Git для восстановления контрольных точек. Определи ветку, HEAD, staged, unstaged и untracked изменения.

Без явного основания и разрешения по `AGENTS.md` не выполняй `reset`, `restore`, `checkout`, `stash`, rebase, переписывание истории и переключение веток.

**Upstream.** Если у ветки есть upstream, зафиксируй известное локальному Git состояние (`git rev-parse --abbrev-ref --symbolic-full-name @{u}`, `git status --short --branch`). Не выполняй `fetch`, `pull`, `merge`, `rebase` автоматически. Локальная информация об upstream может быть устаревшей — не утверждай, что ветка синхронизирована, если это не проверено. Расхождение с remote само по себе не повод менять базу задачи.

## 5. Виды состояния

Не объединяй в одну иерархию разные виды информации:

| Вид                       | Вопрос                                               | Откуда                                                                                                                              |
| ------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Repository state          | что фактически лежит в репозитории сейчас            | ветка и HEAD, index, working tree, untracked-файлы задачи, код, конфигурация, generated output                                      |
| Verified behavior         | что из текущего состояния действительно подтверждено | только проверки, выполненные против релевантного состояния кода; старый PASS — история и не подтверждает код, изменённый после него |
| Task intent и progression | что задумано и где работа                            | текущая инструкция пользователя, задача Backlog.md, `WORKLOG.md`, заметки; старые handoff и summaries — вспомогательно              |
| Обязательные правила      | как реализация должна быть устроена                  | `AGENTS.md`, действующие ADR, `docs/project/conventions.md`, контракты                                                              |

Существующий код не отменяет обязательное правило только потому, что нарушение уже есть в репозитории.

---

## 6. Классифицируй текущие изменения

Не угадывай автора staged и unstaged изменений: Git обычно не позволяет это надёжно установить. Классифицируй изменения по отношению к задаче:

- **TASK-RELATED** — связь подтверждается планом, `WORKLOG.md`, заметками, scope, критериями приёмки, окружающей реализацией или очевидным продолжением изменения. Это часть незавершённой реализации.
- **UNRELATED** — очевидно другая работа: сохраняй нетронутой и не включай в scope.
- **UNKNOWN** — назначение или происхождение не установить: не откатывай и не переписывай без необходимости. Если следующий шаг пересекается с таким изменением и безопасно продолжить нельзя — это блокер.

Не считай весь dirty worktree автоматически «пользовательскими изменениями» или «работой прошлого агента».

Состояние задачи может лежать в нескольких слоях: committed baseline → коммиты задачи → staged → unstaged → untracked-файлы задачи. Учитывай все. Незакоммиченное изменение — не повод считать, что работы нет; написанный код — не повод считать её проверенной. Для каждого существенного участка определи: завершён и проверен; реализован, но не проверен; частично реализован; не начат; требует пересмотра из-за нового evidence.

## 7. Сверка (reconciliation)

Сравни цель, критерии приёмки, план и заметки задачи, `WORKLOG.md`, Git state, фактический код, generated output и известные результаты проверок. Определи расхождения:

- **Задача говорит «сделано», репозиторий не подтверждает** — прав фактический код; не пропускай шаг из-за старой отметки.
- **Код уже есть, а план считает шаг незавершённым** — не выполняй повторно; определи, что реально осталось: проверка, чистка, интеграция, документация, ревью или следующий шаг.
- **`WORKLOG.md` устарел** — прав Git: обнови `WORKLOG.md` сразу (`AGENTS.md`, «Восстановление контекста»).
- **План устарел** — если изменение локальное, очевидно следует из нового evidence и не меняет архитектуру, контракты и scope, актуализируй план задачи Backlog.md. Если нужно новое архитектурное решение, изменение публичного контракта, существенное изменение scope или дорогое в отмене решение — не угадывай, это точка решения для пользователя.
- **Решение уже есть в текущей инструкции** — если нужное решение однозначно дано в текущем сообщении пользователя («отказались от X, делаем Y»), повторно его не запрашивай. Согласуй с ним задачу Backlog.md — критерии приёмки, scope, план, заметки, только где это действительно нужно — и продолжай. В заметки задачи запиши, что изменение — решение пользователя, с датой и сутью: тогда последующая проверка (`audit-after-changes.md`, `review-implementation.md`) увидит подтверждённое изменение scope, а не критерии, переписанные задним числом. Точка решения возникает, только если нужного решения ещё нет или инструкция допускает несколько существенных трактовок.

## 8. Точка продолжения

До изменения кода восстанови для себя:

```text
Task:
Current repository state:
Current verified state:
Already completed:
Implemented but not verified:
Remaining:
Blocked by: нет / <внешнее условие и условие снятия>
Next concrete step:
```

Не превращай это в большой отчёт: главный результат восстановления — **переход к работе**.

### Нет выполнимого шага: всё ждёт внешнего условия

Если все оставшиеся шаги ждут внешнего условия (решения или действия пользователя, доступа, удалённого репозитория, окружения), выполнимого `Next concrete step` нет:

1. сообщи, что именно осталось и какое условие снимет блокер (`AGENTS.md` требует называть условие снятия);
2. если `WORKLOG.md` или заметки задачи не отражают это состояние — обнови их;
3. **не начинай новую работу вне плана**, чтобы «сделать что-то полезное», и не отмечай заблокированный шаг выполненным;
4. остановись со статусом «ждёт внешнего условия».

Это не `BLOCKED` из-за неясности: состояние понятно, нужно действие вне репозитория.

---

## 9. Продолжай

Если выполнимый следующий шаг определён и блокера нет — после короткого сообщения о восстановлении **в том же ходе** переходи к его выполнению. Не останавливайся на «восстановил состояние, следующий шаг X» и не спрашивай «Продолжить?», если задача и шаг однозначны.

Перед каждым шагом проверяй, действительно ли он ещё нужен: не переписывай работающий код, не повторяй завершённую миграцию, не создавай существующие файлы, не добавляй зависимость повторно, не реализуй заново выполненный критерий, не повторяй исследование, если его вывод подтверждён текущим evidence. Старые результаты проверок — история, а не доказательство последующих изменений.

**По существующему плану:** найди первый реально незавершённый шаг, выполни его и предусмотренную проверку, обнови контрольную точку, переходи к следующему зависимому шагу. Не составляй новый план целиком без необходимости; если план требует изменения — актуализируй план задачи Backlog.md, а не создавай параллельный в чате или файле.

### По уровню задачи

- **SMALL** (по `AGENTS.md` без задачи и журнала): восстанови состояние по Git и коду, продолжи с первого незавершённого действия, выполни соразмерную проверку, не создавай процессную документацию ради формальности. Задачу, уже оформленную как STANDARD/LONG, задним числом не понижай.
- **STANDARD**: план в задаче Backlog.md, `WORKLOG.md` по порядку работы, контрольные точки, обязательные проверки и финальный просмотр диффа.
- **LONG**: восстанови родительскую задачу, подзадачи, зависимости, текущую активную подзадачу и завершённые контрольные точки. Продолжай **с текущей незавершённой подзадачи**, а не с начала плана родителя; не начинай зависимую подзадачу, пока предпосылка фактически не выполнена. Если подзадачи могли меняться параллельно в другой сессии, перед продолжением перепроверь репозиторий и задачи.

### Особые случаи

- **Bug fix**: если root cause подтверждён и согласуется с текущим evidence — не расследуй заново, продолжай с текущей стадии (исправление → проверка исходного сценария → regression protection → финальные проверки). Если новое evidence опровергает причину — не продолжай speculative fix, вернись к `investigate-bug.md`.

## 10. Проверки, процессы, ревью

После восстановления продолжай по AGENTS.md, docs/project/quality-checks.md и существующим манифестам. Запускай `npm run check:agents` и применимые проверки приложения только после проверки наличия команд и файлов. Результаты до последующих изменений не считаются актуальными; недоступные проверки укажи в отчёте.

**Второй проход ревью.** Если он обязателен, собственная повторная проверка исполнителя его **не заменяет**: используй subagent `reviewer`, `review-implementation.md` в отдельной сессии или другой механизм проекта с отдельным контекстом. Если выполнить его в текущей среде невозможно — оставь `PENDING`, не объявляй выполненным и не называй self-review независимым.

**Контрольные точки** (STANDARD/LONG) — по `AGENTS.md` после каждого значимого результата: что сделано, что проверено, что изменилось относительно плана, что осталось, с какого места продолжать. `WORKLOG.md` — рабочая память одной задачи, а не журнал истории. Перед паузой, передачей или концом сессии перенеси контрольную точку в заметки задачи.

---

## 11. Стадии завершения

Не объявляй задачу завершённой только потому, что код написан:

```text
implementation in progress → implementation complete → verification complete → review complete → task closure complete
```

- **Готова к проверке** — код написан, обязательные проверки не выполнены.
- **Готова к ревью** — реализация и обязательные проверки завершены, обязательный второй проход ревью не выполнен.
- **Завершена** — выполнены обязательные критерии приёмки, проверки, согласованность генерации, контракты, документация и ADR при необходимости, обязательный второй проход, финальный просмотр диффа и закрытие по `AGENTS.md`: итоговое резюме, отмеченные фактически выполненные критерии, `PROGRESS.md` при необходимости, статус `Done`, возврат `WORKLOG.md` к шаблону.

---

## 12. Когда остановиться

Не продолжай на догадке, если обнаружено: несколько активных задач без указания пользователя; UNKNOWN-изменение, с которым придётся конфликтовать; новое архитектурное решение; незапланированное изменение публичного контракта; неподтверждённый root cause бага; сломанная предпосылка; конфликт требования пользователя с обязательными правилами; необходимость разрушительной Git-операции, коммита или push без разрешения в текущей сессии; изменение production или общих удалённых данных без разрешения; невозможность безопасно определить следующий шаг.

В таком случае сохрани фактическое рабочее состояние, зафиксируй блокер, точно укажи точку решения и не выполняй speculative implementation. Ожидание внешнего условия — раздел 8.

# Формат рабочего поведения

Обычно достаточно короткого сообщения, после которого **в том же ходе** продолжается работа:

```text
Продолжаю TASK-123.

Восстановлено:
- ...

Текущая точка:
...

Следующий шаг:
...
```

При существенном расхождении:

```text
Обнаружено расхождение состояния:

Backlog: ...
WORKLOG: ...
Git / code: ...
Фактическое состояние: ...
Действие: ...
```

Если сверку можно безопасно выполнить по порядку работы проекта — выполни и продолжай. Если нужно решение пользователя — остановись только на этой точке решения.

Шаблон ниже — формат ответа, а не продолжение инструкций.

```markdown
## Результат

**Task:** TASK-...

**Продолжено с:** ...

**Сделано:**

- ...

**Проверено:**

- `...` — PASS
```

# Инварианты

1. **Сначала восстанови состояние по протоколу `AGENTS.md`, затем продолжай — не начинай задачу заново.**
2. **Текущая инструкция пользователя отделяется от прошлого контекста; разрешения из прошлых сессий не переносятся.**
3. **Единственная задача в `In Progress` — кандидат; при нескольких без указания пользователя — спроси.**
4. **Repository state, verified behavior, task intent и обязательные правила — разные виды информации. В вопросе фактического текущего состояния приоритет у repository state; в вопросе обязательных ограничений — у `AGENTS.md`, действующих ADR и контрактов.**
5. **Не угадывай автора dirty diff — классифицируй изменения по отношению к задаче; чужие и неизвестные не трогай.**
6. **Не повторяй выполненную работу и не считай написанный, но непроверенный код завершённым.**
7. **Если план устарел — актуализируй план задачи Backlog.md, а не создавай второй source of truth.**
8. **Без разрушительных Git-операций, fetch, pull и rebase ради восстановления; generated code меняется через источник.**
9. **Обязательный второй проход ревью не заменяется собственной проверкой исполнителя.**
10. **Если выполнимого шага нет из-за внешнего условия — назови условие и остановись, не придумывая работу.**
11. **После восстановления немедленно продолжай, если выполнимый шаг есть и блокера нет.**
